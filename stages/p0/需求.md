# P0 需求：dsh-plugin-kit 重定义

> 2026-11-13 定稿。本文件取代历史上所有对「阶段门 / 台账 / 拦截」的产品定位；
> 定位为什么变，依据与取舍在 ADR（P1 产出），本文件只回答「要什么、怎么算有」。
> 旧定位的完整历史在 git（`77ef98f` 及之前），不在本文档里。

## 一、问题定义（这个插件为什么值得存在）

服务对象：**在 DSH 上、与 AI 执行者协作开发插件的人。**

### 痛点一：宿主是黑盒（结构性痛点，与开发者是谁无关）

三个成因全部是平台性质，换任何人来开发、每一次开发都会撞上：

1. 宿主本体封在约 208MB 的 `app.asar` 里（实测 208,137,981 字节），`grep` / `glob` 物理打不开；
2. 宿主 API 无公开文档，真实契约只存在于运行时（inspect）与安装包源码里；
3. 离线 Node 环境与宿主加载环境不同——本地合法的代码在宿主里非法（ESM client.js 实证）。

后果：开发者对着一份**猜出来的契约**写代码。实证：一次真实开发为确认宿主契约花费 200+ 次工具调用（`SKILL.md`「查不出答案时的顺序」节）。

### 痛点二：「完成」没有权威定义，且升级后复发

代码写完、测试全绿之后，**没有任何权威清单告诉开发者：什么算装上了、什么算能用了、宿主升级后要重验什么。** 这些知识只散落在一次次真机崩溃里，收敛为四大失败家族：

| 失败家族 | 具体形态 | 在哪暴露 |
|---|---|---|
| **装不上** | 缺 `dsh.bundle.patch`；patch 行 id 与包名不一致；Config 是普通对象；inject 猜了不存在的服务 | install 那一刻 |
| **装上了但看不见** | skill 缺 `resourceBase`（模型不知道文件在哪）；slot 注册塞进 inject 回调 | 用户打开界面那一刻 |
| **一加载就崩** | client.js 含 ESM export（宿主把所有插件 client.js 拼成一个大脚本）→ 整个 web boot 崩 | 重启那一刻 |
| **环境相关** | 最小 profile 能激活，混进完整插件集就 `1 entry did not activate` | 换环境那一刻 |

新手只能用自己的崩溃把这张清单重踩一遍。且 DSH 升级 = 清单刷新一遍（rc.1→rc.2 实证：升级后「要重验什么」无任何机制提示；宿主新增 `fs/write-intent` 等接缝，旧副本与旧清单都不知道）。

**两个痛点的两面性**：同一个黑盒——写的时候不知道它要什么（契约），写完不知道它认不认（验证）。

## 二、核心目标

> **让插件开发者在写代码之前就知道宿主要什么（契约知识），在宣称完成之前就知道要验证什么、怎么验证（可执行验证清单）——并且这两样知识随宿主升级持续保鲜。**

## 三、产品形态（要产出什么；实现方式 P1 裁定）

1. **契约知识**（skill 正文）：查契约的三步顺序（inspect → 可检索副本 → 找同类真实插件读源码）+ 宿主四份文档的可检索副本（随宿主版本重解）+ 副本过期判据（asar mtime vs extractedAt）。
2. **验证清单的可执行形态**（脚本）：对任意插件项目可跑的自检——四大失败家族逐条有核查项，每条输出 PASS / FAIL / UNVERIFIABLE，FAIL 附「缺什么、怎么补」。升级保鲜 = 触点复检（现有 `recheck.mjs`）与首装自检的合并或并列（P1 裁定）。
3. **分发载体**（插件 Host 半）：把上面两样注册进宿主 skill 目录，免手动复制。**仅此**——不再含拦截、台账、纪律段。

## 四、逐条验收标准

每条 = 操作 → 观察 → 判定。机判 9 条 + 人工判读 1 条（A8，P3.5 实测补），共 10 条。

| # | 操作 | 观察 | 判定 |
|---|---|---|---|
| A1 | 按 `VERSION.json` 记载来源从 rc.2 asar 重解副本 | 抽查 ≥3 个文件（含 `cordis-plugin-development/SKILL.md` 与至少一份 references）与 asar 原文一致 | `VERSION.json.dsh == "0.2.2-rc.2"` 且抽查零差异（hash 机判） |
| A2 | 在 `host-skills/` 全目录 grep `fs/write-intent` | **修订（P1.5 实测）**：dsh-doc 文档不逐条记载 fs/*-intent 事件（宿主文档只讲机制原则，事件全集以 inspect 为权威源）。改为：①副本含 dsh-doc 43 文件且 `VERSION.json.dsh == "0.2.2-rc.2"`；②`practices.md` 载明「Confirm every Service method, Event name… through cordis_inspect_query」（文档确认 inspect 为权威源的条款在位） | ①②均机判；②不在位判 FAIL |
| A3 | 读新 `SKILL.md` | 三步查契约顺序各带「什么时候用 + 判据」 | 锚点词机判（readme-claims 式断言） |
| A4 | 对照四大失败家族逐条找核查项 | 每个家族 ≥2 条核查项，每条带「查什么 + 什么算过」 | 无空家族（条目数机判） |
| A5 | 对模板项目注入缺陷并跑自检：装不上家族 3 个（删 `dsh.bundle.patch` / patch name 改一半 / `Config` 改普通对象）、一加载就崩家族 1 个（client.js 加 `export`）；「装上了但看不见」家族补 1 个（skill 定义缺 `resourceBase`，判据依托 `lib/skill-provider.js` 的 `isValidDefinition`）；「环境相关」家族不注入——它只能在真机完整插件集里复现，标 `UNVERIFIABLE`，理由见 process.md P3.5 完整插件集条款 | 每次注入对应项变红；复原后全绿 | 5/5 红 + 复原绿（mutate 式机判）+ 1 条 `UNVERIFIABLE` 留痕 |
| A6 | 把 skill 目录 + 脚本复制到无本包其余部分的新项目跑 | 脚本可执行、`SKILL.md` 相对链接全部存在 | 零死链 + 脚本 exit 0（机判） |
| A7 | 模拟升级：把 `VERSION.json` 的 `extractedAt` 改成早于当前 `app.asar` mtime 的时刻 → 过期判据应报「副本可能过期」 | 判据（asar mtime > extractedAt）触发 | 判据有效（机判）；反向复原后判据不触发 |
| A8 | 装包 → 加载 skill → 在插件项目跑自检 | 见第五节，三项屏幕观察 | 人工判读，L1，P3.5 一次性 profile 实测 |
| A9 | grep 产品代码（`index.js` / `lib/` / `vendor/config.js`），模式集：`tools/pre-execute`、`tools/result`、`enforce`、`createLedger`、`systemPrompt.section` | 全部零命中（`discipline.js` 整文件删除） | 六模式零命中（机判）+ CHANGELOG/ADR 指明归档位置（git 即归档） |
| A10 | `npm run check` | exit 0 | 机判 |

**验收计数机检**：机判 9（A1–A7、A9、A10，其中 A5 含 5 红 + 1 留痕）+ 人工判读 1（A8）= **10 条**。

## 五、用户可见面（强制项）

| 操作 | 用户在宿主界面看到什么 |
|---|---|
| `install_bundle` 本包后 | skill 目录出现 `plugin-kit`（插件页列表、会话内问模型「有哪些 skill」均可见） |
| 模型加载 `plugin-kit` | 读到的正文是新判据（查契约顺序 + 失败家族清单），能复述「四大失败家族」；旧九阶段内容**不再出现在 SKILL.md 正文**（旧 references 是否随包保留由 P1 裁定，若保留必须标退役并从导航移除，使「复述旧流程」失去正文来源） |
| 在插件项目里跑自检脚本 | 终端逐项 ✓ / ✗ / UNVERIFIABLE 报告；FAIL 项屏幕上带「缺什么、怎么补」 |

## 六、歧义清单

| 歧义 | 归属 |

| Host 半最终剩什么（仅 skill provider？） | 自查可解（P1 裁定） |

歧义全部自查可解，无上抛项（用户已明确技术决策全权授权）。

## 七、不做清单

| 不做 | 反驳「那做个 X 行不行」的依据 |
|---|---|
| 拦截 / enforce | 证伪：真实开发会话中 17 拦 0 真阳性，拦掉的全是只读工具与审查派发（裁定书；注意其自身告诫：门真正只运行 134 分钟，「17 次」含争议，方向性结论不变） |
| 阶段门 / 九阶段机制 | 单作者事故史长出的形状；判据**内容**降级为参考资料并入新 skill，**机制**退役 |
| 作证台账（witness / actor 关联 / 自签检测） | 未验证假设（依赖单作者实验的「AI 伪造」场景）；**搁置非否定**，复活条件 = 多智能体协作使「谁干的」成为日常痛点 |
| host-skills 自动同步 | 拿运行时稳定性换文档新鲜度，原裁定保留（手动重解一次即可） |
| GATE.json 防伪 / 签名 | 超范围，原裁定保留 |
| 设置页 / GUI | 无对应痛点；契约知识与自检脚本的界面就是终端输出 |

## 八、证据边界（本需求的成立条件）

| 断言 | 等级 | 说明 |
|---|---|---|
| 痛点一是结构性痛点 | L2 | 平台性质推理（asar 封闭 / 无文档 / 环境差异三条与开发者无关）；「200 次调用」是 L3 单作者记录 |
| 四大失败家族 | L3 | 单作者事故史归纳；「换人也遇到」未验证（承 `evidence.md` 边界二） |
| rc.2 新增 `fs/*-intent` | **L1** | 活体宿主 inspect Event 目录实测（2026-11-13） |
| 自检判定式 | L3 | 三分之二来自本仓现存测试（`template.mjs` 13 项、`packed.mjs` 6 项），其余来自 `process.md` P3.5 条款文本——**client.js 拼接（ESM）检查目前无任何现存测试依托**（grep 零命中），P1 按新建规划，为 A5 最难的一条 |
| 「副本过期 → 升级后必须重验」 | L2 | 本仓自身刚经历（rc.1 副本对 rc.2 已漏三个新事件） |
