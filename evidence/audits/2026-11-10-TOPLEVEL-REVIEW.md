## 一、先把你的话翻译一遍

### 1.1 三句原话在做三件事

| 你的话 | 它在要求什么 |
|---|---|
| 「从 dsh-plugin-kit 顶层设计出发」 | 不是问某条规则对不对，是问**这个产品的第一性假设还成不成立**——它假设「AI 交付失败的主要原因是作者自评不可靠」，这个假设要不要换 |
| 「效率维度啊，或者其他维度，维度该你来想」 | 你要的不是一张 KPI 表，是**几个互相独立、至少有一个能推翻现有假设的观察角度**；你授权我定义它们 |
| 「把数据重新分析，考虑这个插件该解决什么问题」 | 要一个**判决**：维持 / 改优先级 / 推翻，并且判决要挂在数字上 |

### 1.2 「顶层设计」我翻译成三个可回答的问题

1. **第一性假设**：它认为失败发生在哪一刻？（现答案：发生在「写的人自己判自己」那一刻）
2. **作用点**：它把自己的强制力插在哪条路径上？（现答案：写路径——`tools/pre-execute` 拦 `stages/` 下的写入）
3. **成本承担者**：谁为它付账，付多少？（现答案：项目里建 `stages/`、每个阶段手写 `GATE.json`、人工开门；E 阶段实测 160→184→204 分钟，见 §3.9）

三个问题里，只要有一个的答案和真实数据不符，产品定位就该调。本文的判决是：**第 1 个成立，第 2 个错了，第 3 个没算清。**

### 1.3 「维度」我翻译成「能证伪的角度」

不是「效率、质量、体验」这种分类筐。一个维度必须满足三条才算数：

- **可数**：能从这 1,146 行里数出来，不是感觉；
- **可分辨**：不同结论会给出不同的数（否则它区分不了假设）；
- **有杀伤**：至少有一个维度的数能直接判现有设计死刑或缓刑。

我提六个，理由和取舍写在 §2。

### 1.4 这和「审计」的分界

| | 审计（你以前做的） | 这次 |
|---|---|---|
| 问句 | 「规则被执行了吗」「审查员抓对了吗」 | 「这些规则该不该存在」「强制力该插在哪」 |
| 证据 | 产物 vs 判据 | **行为分布**：调用、重复、停顿、返工、漂移 |
| 结论形态 | 符合性结论（PASS/FAIL） | 必要性结论（保留/降级/换主产物） |
| 失败代价 | 漏一个缺陷 | 把工程投在一个不产生收益的位置上 |

所以本文**不评价** 23 条铁律写得对不对、133 条测试够不够。它们可能都对——对，但不重要。

## 二、六个维度，以及为什么是这六个

| # | 维度 | 回答什么问题 | 为什么这组数据支撑它 | 一句话结论 |

**为什么不是「效率」一个维度**：墙钟 109 分钟里 90.1 分钟是模型自己在生成（含 46 次传输重试和 2 次 max-tokens 截断），工具执行只有 12.4 分钟、后台命令 4.5 分钟。用分钟衡量产品，量到的是中转站和模型，不是机制。

**为什么不是「成本」单独一个维度**：成本已经有人算过了（`COST-VERDICT.md`），而且算出了三个不同的总数（§3.9）。再加一个成本维度只会重复它，不会推翻它。

**为什么保留 D3（机制占用率）**：这是唯一能直接回答「这东西该不该是现在这个样子」的维度——一个机制如果在其唯一一次完整真实使用里触发 0 次，它的问题不是好不好，是有没有。

### 3.2 D1 注意力账本：读 65%，写 12%

2. **产品的判据层也只覆盖写作阶段。** 九张阶段卡里，P2 是唯一「写代码」的卡（`process.md:151-167`），其余八张都是写作前的纸面产物或写之后的验收。真实会话里，写作只占 11.6%，纸面产物占 **0%**（见 D3）。
3. **「效率」如果按调用数算，可优化的池子在读那一侧。** 按分钟算不可优化——90 分钟是模型在生成，不是机制在挡。

**这一维对现有定位的判决：缓刑。** 不是「拦截没用」，是「拦截的位置只覆盖了 11.6% 的工作量，而且这 11.6% 在这份样本里没有一次出错」。

### 3.4 D3 机制占用率：三样能力，一次完整真实使用中的触发次数

产品自称三样东西（`README.md:3`）：判据（skill）、纪律（systemPrompt）、强制力（pre-execute）。逐个数：

|---|---|---|---|
| 判据 skill | 开工前 | **1 次加载**（0.3 分钟，seq31） | `skill {"name":"plugin-kit"}` |
| 纪律段 | 每一步 | **注入了，但自己关了** | 系统提示里原文：`如果没有 .stage-gate.json，忽略本段`（`lib/discipline.js:48-54`，日志系统中出现 2 次） |
| 强制力 | 写阶段产物时 | **0 次**：0 次写入落在 `stages/`，0 个 `GATE.json`，0 行 `_ledger.jsonl` | 22 次写全在 `dsh-archive-purge/` 下 |
| 审查员 | 每阶段结束 | **0 次**（0 次 `subagent` 调用，`delegationDepth: 0`） | 工具直方图无 `subagent` |
| 阶段产物 | P0…P5 | **0 个** | 无 `stages/` 写入 |

链条是这样的，清楚到不需要解释：第 0.3 分钟纪律段要求「先加载 plugin-kit」→ 第 0.3 分钟 AI 照做；第 0.4 分钟 AI 去查 `.stage-gate.json`（seq36）→ **`No files found`**（seq37）→ 纪律段自己说「忽略本段」→ 之后 108 分钟，产品的一切机制再没有出现过。`README.md:240` 自己写着这是「根本限制」。

补充两个对照，避免把话说绝：

- **上一场（E 阶段，`dsh-archive-manager`）确实开了门、开了审查员**：`stages/` 下有 p1/p2 各两份 REVIEW + RE-REVIEW，共 4 份审查报告；`cost-log.md` 里有 6 行「开门? 是」。所以审查员机制不是没被用过。
- **但上一场也没留下机器可读的门记录**：全树 **0 个 `GATE.json`**、**0 行 `_ledger.jsonl`**（我按文件名递归查过）。6 次「开门」在 `cost-log.md` 里是手写的「是」，不是门插件写的记录。**两个真实项目，插件形态的强制力一次都没有留下痕迹。**

**这一维对现有定位的判决：这是最硬的一刀。** 强制力不是「偶尔没生效」，是「在真实任务里没有触发路径」：marker 是可选的人工动作，不建就完全放行，而 AI 没有任何理由去建它——因为它不建也能把活干完（干成干不成是另一回事）。产品把「是否启用自己」的决定权，交给了它想约束的那一方。

顺带说清事实边界：你记得「把宿主搞崩过两次」。**这份日志只能证到一次**（91.2 分钟的 `1 entry did not activate`，发生在会话自己建的一次性 profile `ap-verify` 里）；另一次在 `dsh-archive-manager` 的记录里（`REAL-HOST-RESULT.md:81-92`：装进 desktop 后 web boot 失败）。而且两次性质不同：91.2 分钟是「宿主半一个条目没激活」，REAL-HOST-RESULT 记的是「整个 web boot 起不来」。别把两条并成一条。

**这一维对现有定位的判决：靶心偏了。** 23 条铁律解决的是「写的人自己判自己」，而这一场败在「读的人不知道自己读到的算不算数」。唯一真正被踩到的铁律是第 5 条「关于宿主能力的断言必须带出处」（`process.md:62`）——踩它的人是 AI，抓住它的应该是审查员，但审查员这一场没被开出来。

两个观察：

1. **前 23 分钟里，人是唯一的纠偏力量。** 两次改向都发生在 AI 已经跑了 34 次调用之后；产品当时在场（skill 已加载、纪律段已注入），零作用。
2. **第 100.2 分钟那条消息，是整场会话唯一一次「宿主真实状态」被确认。** AI 自己拿到的是 `pending`——它把 `pending` 解释成「等浏览器连上就好」（95.4 分钟、96.2 分钟的推理原文），并据此让你去开浏览器（99.4 分钟，等了 90 秒）。**是你打开页面看到报错，才把这个状态变成事实。**

产品的定位句是「把检查从写的人手里拿走」（`SKILL.md:8`）。这份数据显示的是：**检查没有被拿走，它被交给了人**——而且交给人的那部分，恰好是 AI 最没有能力自证的那部分（宿主运行时状态）。

### 3.7 D6 外部噪声：82.7% 的墙钟不归产品管

- 模型步内耗时 90.1 / 109.0 分钟；
- 46 次传输重试：42 次 `Connection error`、2 次 `ECONNRESET`、2 次 `TIMEOUT`；重试退避合计只有 82 秒，也就是说**慢不在退避，在每次重试背后的请求本身**；
- 第 18.2 分钟模型被换掉：`our-free-model/kilo-auto/free → sn/sensenova-6.8-flash`（seq180）；
- 2 个轮次以 `max-tokens` 结束（turn 1、turn 2），这两轮合计 876 秒（14.6 分钟），期间分别有 341 秒、375 秒的静默段。

结论：**任何用分钟数论证这套机制「划算/不划算」的结论，都必须先扣掉这 82.7%。** 反过来，本文所有「效率」判断都用**调用数/步数**，不用分钟数。这也是我不接受 `COST-VERDICT.md` 那套「288 分钟止损线」口径的第二个理由（第一个理由是分母凭空估，他们自己已经承认，见 `COST-VERDICT.md:51-52`）。

## 四、结论

### 4.1 一句话

**不推翻定位，推翻优先级。** 它现在把自己做成了「写路径的流程警察」，而这份数据说瓶颈在「读路径的事实副本」——**该解决的是「关于宿主的每个断言，当场可证伪」，审查员只是执行这件事的一种方式，不该是产品的主语。**

### 4.2 三条判断

**判断一：第一性假设成立，但它是「必要条件」不是「充分条件」。**
「作者自评抓不到自己的错」——这条没有被这份数据推翻，也没被验证：审查员在这场 0 次出场。它成立的理由是逻辑的（立场问题），不是数据的。而这场会话证明了另一半：**即使作者愿意被审，只要「事实」本身没有登记处，审查员审的也是两份互相矛盾的散文。**

**判断二：优先级倒置，且可以量化。**
- 产品最强的工程（`pre-execute` 强制拦截 + 133 条测试 + 9 张阶段卡 + marker）守的是 **22 次写（11.6%）**；
- 真实成本在 **123 次读（65.1%）**，产品在这一侧的供给是「去内置 skill 找」，而内置 skill 自己承认没写全（`tools.md:29`、`process.md:207`）；
- 强制力在两个真实项目里留下 **0 个 `GATE.json`、0 行台账**（§3.4）。它守的那 11.6%，在这场里一次错都没出。

**判断三：产品的成长方式不可持续。**
每场事故 → 加一条铁律。三轮实验 23 条（`process.md:48`），E 阶段又加了 C4/C5/C6 和「完整插件集条款」（`process.md:238-242`），这场会话按同样逻辑还能再加 4 条（服务是否存在、`pending` ≠ 健康、asar 与 asar.unpacked 的区别、`inspect` 入参怎么给）。文档已经 **72 KB 散文**（SKILL 7.1K + 7 份 references 61.3K + README 4.0K），而这场会话只消费了其中约 14 KB（`tools.md` 全读 11.4K、`walkthrough.md` 部分、`process.md` 两次 grep）——**19% 的消费率**。继续加，边际收益会掉到零，因为没人读得完。

### 4.3 依据映射（结论 ← 维度 ← 数字）

| 结论 | 维度 | 关键数字 |
|---|---|---|
| 作用点选错（守写不守读） | D1 | 读 123 次 65.1% vs 写 22 次 11.6% |
| 探测不累积、不终止 | D2 | 22 次探测 7 次完全重复；49KB 目录取 4 次占工具输出 28.4%；同一问题 grep 15 次；42 分钟 74 次调用零结论 |
| 强制力在真实任务里没有触发路径 | D3 | marker 0、GATE.json 0、台账 0、审查员 0、stages 写入 0 |
| 规则靶心偏了 | D4 | 22 个错误 + 2 次启动失败，0 条落在 23 条铁律针对的失败类；唯一被踩的是铁律 5 |
| 人被当成宿主状态传感器 | D5 | 9 条消息 / 5 次改向 / 427 秒等待 / 唯一一次宿主状态确认来自用户 |
| 不能用分钟数论证机制 | D6 | 模型时间 90.1/109.0 = 82.7%；46 次重试 |
| 事实多副本必然漂移 | §3.9 | 同一实验 172/184/204 三个时长、10/12 两个问题数 |

### 4.4 该做成什么（按优先级，每条带验收判据）

**第一件：宿主契约账本（主产物，替代「流程规格」当第一入口）**

- 内容：每条接缝一行 —— `id / surface / 代码里怎么写 / 证据出处（file:line 或 命令+返回）/ 证据等级 L1-L4 / 最后验证的 DSH 版本 / 不成立时本插件会怎样 / 重验命令 / 反向证据（怎么证明它不存在）`。
- 关键：**跨项目、跨会话共享，装在插件里，不在项目里**。产品已经有一半——`assets/touchpoints.sample.json`、`assets/host-snapshot.sample.json`、`scripts/recheck.mjs`、`P5` 卡（`process.md:304-315`）——但它们被放在「发布后维护」阶段，且是**项目私有**的。把它提到 P0 之前，变成公共资产。
- 验收判据（可判真假）：**新会话问「客户端半能不能触发宿主半删文件」，答案必须来自账本，全程 0 次 `grep`/`read` 宿主源码。** 用这场会话衡量：现状是 15 次同题 grep + 22 次 inspect（含 4 次重复取同一目录）+ 22 次 `dshmarket` 探查，合计远超目标；目标 ≤3 次（查账本 + 跑一次重验命令）。

**第二件：开工前 boot 探针（把 P3.5 的机制前移成 P0.5 的工具）**

- 一个 15 行的空插件（只有 `inject` + 一句 `logger.info('alive')`），一条命令装进一次性 profile、启动、抓 stderr、拆掉。2 分钟内回答「这个 inject 名字到底会不会解析」。
- 数据依据：**这场会话所有真正的契约事实都来自启动**——91.2 分钟的宿主报错、94.5 分钟的 `pending`、105.5 分钟从 boot payload 读到的 client 注入名；而 100 次 `read`/`grep`/`glob` 加 22 次 `inspect`，没有一次给出桥的正面答案（只给出了若干「不存在」的负结论）。
- 验收判据：从「怀疑某条接缝」到「拿到宿主报错或成功日志」≤3 次工具调用。现状：从 53.2 分钟知道缺通道，到 91.2 分钟才第一次启动，**38 分钟**。
- 注意：这会把「每改一次验一次」的成本从「2 分钟人工」压到「一条命令」，因为探针插件永远不变，变的是被验的那一行。

**第三件：断言对账（这才是 `pre-execute` 该拦的东西）**

- 规则：代码里出现 `inject:` 的每个键、`ctx.<service>`、`host.call('<method>')`，都必须在账本里有条目且状态不是 `unverified`；否则 deny 并回一句「账本里没有 `host`，最近一次验证：不存在（seq91，56 个服务无此项）」。
- 数据依据：92.9 分钟的 `inject:['host']` 是致命动作，账本里恰好没有这条；一次 deny 就能把 91.8 分钟压成 0。
- 验收判据：拿这场会话的 `index.js` 当回归样本，这条检查必须变红；把 `host` 换成 `workspaceFiles` 必须变绿。
- 这一步的价值在于：**它把铁律 5 从「审查员要记得查」变成「写不进去」。** 这也回答了产品自己的问题——强制力该插在哪：不是 `stages/` 目录，是**依赖声明**。

**降级（不是删除）**

- 9 张阶段卡、`GATE.json`、marker、审查员任务书：保留，作为「人要介入时怎么介入」的手册。但不再是主入口。
- 理由不是它们错，是它们**没有被触发的路径**（D3），而它们守的路径不是瓶颈（D1）。一个只在有人主动启用时才生效的机制，不该是产品的第一句话。

### 4.5 如果你只想改一件事

**把 `README.md` 的第一句从「三样东西：判据 + 纪律 + 强制力」改成「一份账本：宿主契约 + 开工前探针 + 断言对账」**，然后把现有 23 条铁律降级为账本的写作规范。

因为这场会话的失败可以完整地写成一句话：**AI 在一份自己取过四次的目录面前，确认了一条目录里没有的服务。** 产品现在没有任何一件东西，能在第 92.9 分钟拦住这句话。

### 4.6 什么情况下我错了

- 如果下一个真实项目里，AI **没有**读盘焦虑（账本已经够用），而失败集中在「测试全绿但没接线」「交付命令没跑」——那 23 条铁律就是对的靶心，我的优先级判断错。
- 如果审查员在下一场被真的开出来，并且**独立地**抓住了「`host` 不在服务目录里」这类错误——那「独立性是主问题」成立，账本只是辅助。
- 如果委托人要的交付物是「给团队看的规范文档」而不是「让 AI 稳定做出能用的插件」——那现状基本够用，只需要修 §3.9 的数字漂移和 §3.4 的触发路径。**这两个目标对应两种产品，得先选。**

2. **审查员机制在这份数据里根本没出场**，所以本场既不能证明它有效，也不能证明它无效。它的价值只由前三轮的记录支撑，而那些记录是自述（`evidence.md:126` 自己也这么说）。
3. **`host` 是否真的不可 inject**——我只知道日志里它没成功（91.2 与 94.5 分钟两次），没有独立验证宿主实现。「宿主没有私有 RPC 注册入口」这个结论是 AI 在 104.8 分钟下的，我未复核。

5. **我读不到 `app.asar`，也没运行任何东西**，所有关于宿主行为的判断都转引自日志或产品文档。

### 5.4 一个必须单独说的补充判断

如果第 5.3 条第 4 点成立（需求本身不可做），那么产品缺的还有**一张「不可做裁决」卡**：在 P0 之后、P1 之前，回答「这个需求的中心能力，宿主有没有接缝；没有的话，降级交付长什么样」。现有九张卡全部假设「东西是做得的」——P0 有「不做清单」（`process.md:118`）但那是范围，不是可行性；P1.5 探针门查的是「依赖是否已验」，前提是先有一张依赖清单（`process.md:143-149`）。

```js
// 2) inspect 重复
const seen = {}; for (const c of calls.filter(c => c.data.name === 'cordis_inspect_query')) {
  const k = JSON.stringify([c.args.platform, c.args.provider, c.args.method, c.args.input ?? null]);
  (seen[k] ||= []).push(c.seq);
}
console.log(Object.entries(seen).filter(([, v]) => v.length > 1));

// 3) 时间线
for (const c of calls) console.log(((c.time - t0) / 60000).toFixed(1) + 'm', c.seq, c.data.name);
```

三条口径提醒（踩过的坑）：

1. `tool/call.data.arguments` 是 **JSON 字符串**，直接取 `.platform` 会全是 `undefined`，会得出「没有重复调用」的假结论。
2. `pwsh` 是后台任务：`tool/call → tool/result` 的间隔是**任务注册**的耗时，不是命令执行的耗时；命令时长要看 `job/registered.startedAt → job/settled.finishedAt`。
3. 步内耗时用 `step/start → 下一条同 step 的 assistant/message`，它包含重试与截断，**不等于**「模型思考时间」，但它是墙钟的主要成分。
