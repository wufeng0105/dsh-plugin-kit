# 03 拦截层存废裁定

> 角色：反方审计员（`d1-adversary`），fresh，未参与 WP1/WP2。
> 任务：两方结论相反，判定「整层删掉」还是「换判据保留」。
> 数据源：`session.v4.jsonl`（5044 事件 / 739 次工具调用 / 763 分钟）、`lib/gate.js`、`index.js`、`test/`、`_sandbox/shanchu/` 的真实产物与门记录、`cordis_inspect_query` 直取宿主工具表与 Service 契约。
> 边界：只读。唯一写的文件是本文件。探针在 `%TEMP%`，末尾清理。

## 标注约定

- **【数据】** = 可复核（命令 + 退出码 / file:line / seq / 文件 mtime）
- **【判断】** = 本文推断

## 0. 裁定

**两方都错。WP1 的结论对了一半（该删什么），WP2 的方案对了一半（该换判据）。但合并起来仍然不是答案——因为它们都漏了同一个根因，而这个根因恰好解释了双方各自最得意的证据。**

### 一句话裁定

> **删掉现阶段这个拦截层（WP1 的方向），但不是因为「拦截无用」——是因为「这个拦截层从未真正运行过」。换判据（WP2 的方向）是在给一台没插电的仪器换刻度盘。先插电，再谈刻度。**

### 裁定表

| 方 | 主张 | 对的部分 | 错的部分 |
|---|---|---|---|
| WP1 | 整层删掉 | **「`skip` 是万能逃生门」「门记录由被约束者签发」「拦的全是门记录和事故记录」——三条我全部复核属实，且比它写的更硬** | **它把「从未生效」的观测当作「机制无效」的证据。** 763 分钟里门真正运行的时间只有 **134 分钟（17.6%）**，前 629 分钟因一个缓存 bug 处于关闭状态。用这段时间的 0 次成功拦截来论证「拦截这个机制没用」，是样本选择错误 |
| WP2 | 换判据保留（R1/R2/R3） | **「取消『未知工具』类别」正确且证据比 WP1 硬**；R2「宁严勿漏」的取舍在方向上诚实 | **R1 的载荷键建立在错误事实上**（真实入参是 `file_path`/`content`/`old_string`/`new_string`，不是 `path`/`after`/`before`）；**R3 为一个当前宿主不存在的工具写规则**；且**整套方案没有修 readGate 的 null 缺陷**——不修它，任何判据都跑在「门永远读不到」的地基上 |

### 我给的第三条路（唯一结论）

**分三刀，按顺序，每刀独立可验：**

| 刀 | 做什么 | 依据 |
|---|---|---|
| **第一刀（必修）** | 修 `readGate` 的 `opts.cwd` 缺陷 + `markerCache` 毒化。**不修这两处，任何关于「判据好不好」的讨论都是空的** | §3.1、§3.2 |
| **第二刀（该删）** | 删 `UNKNOWN_WRITE_TOOL` / `READ_ONLY_TOOLS` / `allowedTools` / `root`·`layout`·`gateFile` 三个静默失效配置。把拦截的**默认模式改为 `observe`** | §Q1 最强点、§Q4 |
| **第三刀（该换）** | **把 `GATE.json` 从「allow/deny 判据」降级为「台账事件」**：写 `stages/<stage>/` 时若台账无该阶段审查结论 → 记 `gate-unverified` + 一次 warn，**不 deny**。同时把 `skip` 这个逃生门从「放行」改成「放行但必须在台账留 `skip` 且计入未审阶段」 | §Q3 |

**这不是「全删」，也不是「换判据保留」——这是「拆掉会拦人的那一半，留下会记账的那一半，并且先把仪器修好再讨论测量。」**

## Q1. WP1「整层删掉」的最强点与最弱点

### 最强的一点

**不是「17 次 0 真阳性」——那个数字有争议。它最强的是这句：**

> **写一份 `skip` 的门记录，门就开了。通行证由被约束者自己签发。**

**【数据】** 三份门记录全部 `verdict: "skip"`，`by` 全部是同一句「user-authorized (代写：lead-agent，非独立审查)」（探针 Q）：

```
p0     verdict=skip   by=user-authorized (代写：lead-agent，非独立审查)
p1     verdict=skip   by=user-authorized (代写：lead-agent，非独立审查)
p1.5   verdict=skip   by=user-authorized (代写：lead-agent，非独立审查)
```

**【数据】** `lib/gate.js:310-312`：`if (gate.verdict === 'skip') return { kind: 'skip-noted', stage: prev };`
`index.js:406-411`：`skip-noted` → `ledger.append(...)` → `return next()`。**放行。**

**【数据】** 而 `by` 字段从未参与判定。我用伪造的 `{verdict:'pass', by:'AI 自己写的，不是人'}` 喂 `decide()`，返回 `{"kind":"allow"}`（探针 B §3）。`parseGate`（`lib/gate.js:194-209`）只校验 `verdict ∈ {pass,fail,skip}`。

**为什么这一点难以反驳**：它不是一个「误拦率高」的问题，是**判据的可满足性被被约束者完全掌握**。任何「换判据」方案（包括 WP2 的 R1/R2/R3）都必须先回答这个问题：**新判据是否也允许执行者自己满足它？** WP2 的三条规则**全部是「目标路径」判据，而目标路径完全由执行者填写**——所以 WP2 换完之后，`skip` 依然是万能钥匙，问题一点没动。

**【判断】** WP1 赢在这一点上，而且这一点比它自己写的更致命：它证明了「门」在结构上不可能约束「愿意写 `skip` 的人」。

### 最弱的一点

**它把「门在这份数据里从未真正运行」的观测，当成了「拦截这个机制无效」的证据。**

**【数据】** 两个独立 bug 让门在 763 分钟里只运行了 134 分钟：

**Bug 1（markerCache 毒化，`index.js:263-269`）**
```js
function adoptionOf(baseDir) {
  if (markerCache.has(baseDir)) return markerCache.get(baseDir);   // 一次 false 永久缓存
  ...
}
```
【数据】`.stage-gate.json` 由 seq 403 的 `pwsh` 复制模板生成（mtime `03:03:25`），而该调用的 `pre-execute` 发生在 `03:03:24`——**早 1 秒，marker 还不存在**。那一次调用把 `{adopted:false}` 写进 `markerCache`，此后 `index.js:362-363` 的 `if (!adopted) return next()` 让**所有**调用直接放行，直到进程重启。

【数据】验证：门首次 deny 在 `12:40:21`（第 629 分钟）。此前 **65 次「旧实现必拦」的非写工具调用，0 次被拒**（探针 H）。而 `03h–12h` 逐小时统计：`denied=0`（探针 E）。

**Bug 2（readGate 恒 null，`index.js:305-310`）**
```js
const target = `${root}/${stage}/${cfg.gateFile}`;  // "stages/p1.5/GATE.json"
const resolved = await ctx.fs.resolve(target);      // 没传 opts.cwd
```
【数据】宿主契约（`cordis_inspect_query` → host/Service/`fs`）：「relative paths resolve against `opts.cwd`」。不传 `cwd` 时基准是后端默认值，**不是会话的 baseDir**。

【数据】**反证：6 次「门文件已在磁盘上却仍报 GATE_MISSING」**（探针 S）：

| deny seq | 时刻 | 需要的门 | 该门 mtime | 报什么 |
|---|---|---|---|---|
| 4134 | 14:31:06 | p0 | **14:31:03**（早 3 秒） | GATE_MISSING |
| 4139 | 14:31:11 | p0 | 14:31:03 | GATE_MISSING |
| 4193 | 14:31:40 | p0 | 14:31:03 | GATE_MISSING |
| 4956 | 14:52:02 | p1.5 | **14:31:58**（早 20 分钟） | GATE_MISSING |
| 4975 | 14:52:15 | p1.5 | 14:31:58 | GATE_MISSING |
| 4985 | 14:52:25 | p1.5 | 14:31:58 | GATE_MISSING |

**若不是 `readGate` 返回 null，这 6 次不可能报「missing」。**

**【判断】** 这意味着：**WP1 统计的 8 次 `GATE_MISSING` 里，有 6 次是读盘 bug，不是判据判定。** 剩下 2 次（seq 4044、4123）报的时间点上也早于对应门文件 mtime，严格说也属同类。**即：8 次 GATE_MISSING 没有一次是「判据正确地判断出门缺失」。**

**【判断】如果 WP1 成立，项目会损失什么**：
不是「强制力」这个卖点（那确实该删）。损失的是**在修好 bug 之后重新评估的机会**。WP1 的结论会导致：管线永久移除 → 再没有人会去查「为什么它 629 分钟没运行」→ **两个真 bug（markerCache 毒化、readGate 无 cwd）随代码一起被删掉，而它们的同类会以别的形式留在 `reconcile`、`isStageWrite`、`ledger` 里。** 删掉一个坏掉的部件，和保护它不被检验，是两件事。

## Q2. WP2「换判据保留」的最强点与最弱点

### 最强的一点

**「取消『未知工具』这个类别」——这是全部材料里最硬的一条，且理由在代码里可以直接看见。**

**【数据】** `lib/gate.js:255-259`：`extractTarget` 返回 `unknown` → `denyOf(UNKNOWN_WRITE_TOOL)`。设计含义是「我不认识你的工具，所以判你有罪」。

**【数据】** 在 739 次真实调用里，这类调用共 **77 次**（探针 E）。其中 9 次实际被拦，被拦的是：`read`×2、`ask_user_question`×2、`list_subagent_models`、`todo_write`、`skill`、`plugin_manager`、`subagent`。**这 9 个没有一个会写工作区。**

**【判断】** 这一点难反驳，是因为它不止是「误拦多」，而是**判据类型错了**：用「工具身份」（静态、需维护、随宿主升级漂移）去代理「调用行为」（动态、可从参数判定）。任何靠维护名单的办法都会输给宿主升级。**我完全接受这一点，第二刀里就包含它。**

### 最弱的一点（两处，都是事实错误）

#### A. R1 的载荷键建立在错误的参数形状上 —— 方案的地基是假的

**这是本次审计最重要的发现。**

**【数据】** `brief-WP2.md:55-58`（以及 `tool-shapes.txt:6-8`）声称：

```
write  → path / operation / before / after    （明确标注「不是 file_path，不是 content」）
edit   → path / before / after                （明确标注「不是 old_string/new_string」）
read   → path / offset / lines
```

**【数据】** 真实会话 739 次调用的入参键（探针 L）：

```
write          content×59 file_path×59
edit           file_path×137 new_string×137 old_string×137
read           file_path×28 limit×17 offset×17
pwsh           command×466 description×466
```

**【数据】** 我又用 `cordis_inspect_query`（host/Tool/listTools）从**当前运行中的宿主**直取：`write` = `{file_path, content, sandbox_permissions, justification}`；`edit` = `{file_path, old_string, new_string, replace_all}`；`read` = `{file_path, offset, limit}`。**与实测完全一致。**

**【数据】** `apply_patch` 在当前宿主工具表里**不存在**；`tool-shapes.txt:17` 记的 `str_replace_editor` 参数只有 `items`。

**【判断】`tool-shapes.txt` 记的不是「调用参数」，是「JSON-Schema 的 properties 目录」。** 判据：它每一行都以 `properties` 起头（第 1 行 `ask_user_question items,properties,id,...`；第 6 行 `write properties,path,operation,before,after`）。`properties` 是 schema 关键字，不是入参键。**把 schema 的字段目录当成入参键名，是这份「从 app.asar 抽的真实形状」的根本误读。**

**后果（探针 M）：**

| 未来形状 | 形状判据命中？ | 后果 |
|---|---|---|
| `{target_file, payload}`（write 改名） | **false** | 只能靠 `WRITE_TOOLS` 兜底 |
| `{target, payload}`（新工具） | **false** | **静默放行** |
| `{file_path, content}`（新工具，键名撞上） | true | 侥幸命中 |

**【判断】** brief 的初衷（`brief-WP2.md:11`）是「取消『工具名』这个判据」。但因为它必须保留 `WRITE_TOOLS` 兜底才不至于 0 命中，**「按工具名判断」根本没被取消，只是从 `UNKNOWN_WRITE_TOOL` 的 fail-closed 变成了「不在 WRITE_TOOLS 里就静默放行」的 fail-open。** 这是把「误伤老实人」换成了「放过所有人」，而那正是 WP1 批评的同一个错误的镜像。

#### B. R2 主动 fail-closed 的代价：数字小，但结论错

**WP2 说这个代价可接受。我量化后的结论是：代价确实小，但「可接受」的理由是错的。**

**【数据】** 按 brief 的 R2 判据（命令含 `stages/<stage>` 且含写意图）重放（探针 I）：

```
含 stages/<stage> 的 shell 调用 = 15（全部 466 条 shell 中的 3.2%）
  其中含写意图 → SUSPECT = 9（1.9%）
  其中无写意图（纯读）→ allow = 6
```

**【判断】「1.9%」这个数字本身支持 WP2**——我不否认。但 WP2 的论证里有一句是错的：「宁严勿漏，因为 shell 是 63% 的通道，而它的写意图识别率只有 50%」。**实际上 R2 的识别率更低，且失败方式是静默的。**

**【数据】** 我用当前 `lib/gate.js:177-178` 的正则，测 6 种等价写盘形态（WP1 也测了同一批）：

```
MISSED  $j='{}'; Set-Content -LiteralPath 'stages/p2/a.md' -Value $j   ← 分号后不在行首，^\s* 锚点失效
MISSED  node -e "require('fs').writeFileSync('stages/p2/a.md','x')"
MISSED  [System.IO.File]::WriteAllText('C:\proj\stages\p2\a.md','x')
MISSED  git checkout -- stages/p2/a.md
CAUGHT  cp a.md stages/p2/a.md
CAUGHT  *** Update File: stages/p1/a.md
```

**【数据】** 另外，探针 N 找到 6 条命令提到 `stages` 但没有 `stages/<stage>` 形态（如 `Get-ChildItem stages -Recurse`、`Get-Content stages\_ledger.jsonl`），**R2 看不见它们**。

**【判断】** R2 的真实代价不是「多问几次门」（那是 1.9%），而是**「它让 WP2 以为自己管住了 63% 的通道，实际上没管住」**。这个代价比 1.9% 的误拦严重，因为它是**虚假的安全感**。

### C. 补充：WP2 两处修法也没对准事实

- **T4**（`brief-WP2.md:135`）说「`apply_patch` 参数名是 `input`」——当前宿主**没有这个工具**。为一个不存在的工具写 R3 和 4 条断言（C6、`brief:161`），优先级错位。
- **T5b** 说「`scanCommandText` 返回第一个命中阶段，应返回最后一个/最深」——这对重定向成立，但对 `cp a.md stages/p2/b.md` 这类**写入目标在右侧、但左侧也有 stages 路径**的情形，返回「最深」不等于「写入目标」。**【判断】这是个新引入的判据，同样没有测试证明它不会把「读 stages/p1 写到 stages/p2」判成 p2（这次是对的）而把「写 stages/p2 读 stages/p1」也判成 p2（这次是错的）——两者文本无法区分。**

## Q3. 第三条路

### 有。而且两方都没提到它。

**先说三条被漏掉的候选（我都验过，都排除或降级）：**

| 候选 | 验证 | 裁决 |
|---|---|---|
| **C1. 保留但只拦一种情况（写 `GATE.json` 本身）** | 【数据】探针 K：`write`→`GATE.json` 全 DENY（#4133/#4138/#4192），`pwsh`→`GATE.json` 全 ALLOWED（#4211/#4218）。**这条规则只会拦住唯一正确的通道，放行绕过通道** | **排除**（方向反了） |
| **C2. 删掉但保留台账（只记录不阻止）** | 【数据】observe 对 UNKNOWN deny **失效**：`index.js:369` 在 `:413` 之前 return（探针 B §1）。所以「只记录」今天做不到，**要先修** | **保留，作为第三刀的主体** |
| **C3. 全交给 skill 判据 + 独立审查** | 【数据】审查有效（9 份报告：5 FAIL、20+ 缺陷），但**四个删除事故一次都没抓到**——审查员的判据停在「文件改对了没」，没覆盖「宿主显示什么」（WP1 Q4 增强二已论证） | **排除**（放大已证实的失败模式） |

### 我推荐的第三刀：**「审查事件台账」——保留记账，取消关口**

#### 形状

```
写 stages/<stage>/ 时：
  台账里已有 [stage, kind=review, verdict∈{pass,skip}]  → 放行，记一行 stage-write
  台账里没有                                             → 放行，记一行 gate-unverified + 一次 warn
                                                          （不 deny，不阻塞，可被事后检索）
门记录不再参与 allow/deny。GATE.json 若存在，只作为台账的一条来源（reconcile 已经在做）。
skip 仍然合法，但台账里标为「未审」，且不可被当 pass 引用。
```

三条规则，**全部不依赖工具参数名**：

- **R-A（怎么知道写了哪个阶段）**：不再从参数里猜路径。**改为在 `tools/result` 之后用产物落盘事实反推**——`index.js:432-465` 的 `reconcile` 已经在扫 `GATE.json`，把它扩展成扫阶段目录即可。这一条顺带解决了 WP2 的弱点 A。
- **R-B（怎么知道审了没）**：读台账的 `review` 记录。**审查员必须是 `subagent`/`spawn_teammate` 派生且不是当前 session**；`by` 字段接上（今天写了从没人读）。
- **R-C（没审怎么办）**：**不 deny**，记 `gate-unverified` + 一次 warn。这是 WP1 Q2 的替代方案，但**只在「未审」这一种情况下降级**，不是在所有情况下都降级。

#### 为什么它比「全删」好

1. **它保住了 WP1 唯一没算清的东西：可查性。** 【数据】真实台账 `stages/_ledger.jsonl` 只有 14 行、5 组重复键、且 `attach()` 从未被调用（`grep '\.attach' index.js` → 0）。**今天的台账连「发生了几次阶段写」都记不准**（59 次写、只记了 0 次成功写）。删掉拦截层不会让台账变好；**第三刀把「记账」变成主线，直接修台账。**
2. **它不让「629 分钟没运行」这种事实再次隐形。** 【数据】门静默关闭了 629 分钟，而 `log()` 没有产生任何一条可见告警（探针 Q：非工具事件里 0 条 stage-gate 日志）。第三刀要求 `gate-unverified` 进台账——**默认 observe 意味着「没拦住」是可查的数字，而不是沉默。**
3. **它不给「全删」留下「从此无人负责审查」的口子。** WP1 的 T9 已承认「降级不能消灭仪式，只能把成本从阻塞降到噪音」——我同意这个判断，并把它变成机制。

#### 为什么它比「换判据」好

1. **不依赖参数键名** → WP2 弱点 A 完全失效。
2. **不需要 `WRITE_TOOLS` 兜底** → 不会从 fail-closed 变 fail-open。
3. **不需要 R2 去追 63% 的 shell 通道** → 弱点 B 消失。
4. **断言可数**：4 条（记 `gate-unverified`、review 存在则放行、warn 只发一次、observe 模式下 0 deny），比 WP2 的 9 条（C1–C9）少且**不包含对不存在工具的测试**。

#### 代价（诚实写）

## Q4. 如果走「换判据保留」，需要什么证据才能证明它真的有用

### 直接回答：**今天的样本不支持任何「换判据后有效」的结论。而且比样本量更严重的问题，是基线不确定。**

**【数据】** 现状有两个互相矛盾的基线：

| 口径 | 拦截数 | 真阳性 | 来源 |
|---|---|---|---|
| WP1 | 17 | 0 | `02-价值评估.md` §0.1 |
| 我方修正 | 17 | **0**（9 UNKNOWN 误拦 + 8 GATE_MISSING，其中 **6 次是 readGate null 导致的事实错误**，其余 2 次也早于门文件 mtime） | 探针 J'、S |
| WP2 隐含 | 17 | 8（把「拦写门记录」算作有效） | `01-门模型审计.md` §3.1 |

**【判断】** 在这三个数达成一致之前，「换判据后 N 次拦截 M 次真阳性」无法比较。**先解决基线。**

### 三条硬要求（按顺序，前一条不过不许进下一条）

**E1. 先修两个 bug，并补两条断言。**

- `readGate` 传 `opts.cwd: baseDir`（`index.js:305-310`）。
- `markerCache` 不要缓存 `adopted:false`，或缓存带失效。
- 断言 1：**门文件在磁盘上存在时，`decide()` 不得返回 `GATE_MISSING`**（用真实文件系统，不用桩）。
- 断言 2：**marker 在本次调用中被创建后，下一次调用必须看到它。**
- 这两条必须先在**当前实现上变红**。红不了 = 断言没测到点。

**【数据】** 现状：`test/gate.test.mjs` 38 条全绿（exit 0），**全部用 `mkReader()` 桩注入 `readGate`，没有一条覆盖 `index.js` 的真实读盘路径**。这就是「离线全绿、真机失效」的又一实例。

**E2. 修 observe，并证明它真的在 observe。**

- 【数据】`index.js:369` 的 UNKNOWN 分支在 `:413` 的 observe 判断之前 return。我用 `decide()` 复现：未知工具返回 `code:'UNKNOWN_WRITE_TOOL'`（探针 B）。
- 修完后要有断言：**`mode:'observe'` 下，939（或任何）次真实调用产生 0 次 deny、N 次 `would-block` 入账，且 N 与 enforce 模式的 deny 数一致。**

**E3. 用新项目跑 observe 收「换判据后」的独立样本。**

- 【判断】这是唯一能区分「判据好」与「旧实现太烂」的办法。现有 764 分钟样本已被两个 bug 污染（629 分钟门未运行 + 6 次读盘错误），**不能作为对照**。
- 停止条件：**1 个完整 P0→P4 周期、≥ 300 次工具调用、≥ 3 次 deny（observe 下即 would-block）。** 少于这个数不下结论。
- 判据：**真阳性率** = 拦到「写未审阶段产物」/ 总 deny。**≥ 50% 才算有用；< 50% 回到本文 §Q3。**

### 「没有新样本怎么办」——我的答案

**【判断】没有新样本就不该换。** 理由：WP2 想拿的收益（误拦 9 → 0），可以用**更便宜、更小、可验证**的方式拿到：

- 把 UNKNOWN **改成放行**（1 行）
- 把 `READ_ONLY_TOOLS` **补全或删掉**（1 行）
- 加 1 条断言「10 个只读工具全部 allow」

这三步不需要重写判定模型（WP2 的 T1/T4/T5/T6/T7 五条、9 条判据、4 个变异）。**用重写判定模型去解决「名单不全」，成本收益不成比例，而且 WP2 的新模型带着一个更糟的 bug（R1 键名全错）。**

**现状：**
> DSH 插件开发流程：同时提供判据（skill）、常驻纪律（systemPrompt 段）和**强制力（未过门拦截）**。装一个包，三样都有。

**【判断】** 理由：

4. **不写「独立审查」进定位**——审查是 skill 的行为，不是包的行为；且 §Q1 已证明「审查会被门自己拦掉」，承诺过大就是重复 WP1 批评过的那个错误。
