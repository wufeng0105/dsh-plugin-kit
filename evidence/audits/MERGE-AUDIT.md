## 2. 一、合并这个方向对不对

### 2.1 §1 的理由成立，但主线选错了

`MERGE-DESIGN.md:12-18` 给的三行「现状」里其实有两个独立痛点：

- **痛点 A（分发）**：`plugin-kit` 每个项目手动复制（:14）。这是硬痛点，有明确失败模式（新项目忘了复制 → 判据失效，且没人会发现）。
- **痛点 B（关系未写明）**：两者关系没有任何交付物写明（:16）。
- **痛点 C（AI 不守约定）**：只在 §二（:39）出现，不在 §1 的论证链里。

而 §1 的结论句选的是最弱的一条当标题——「用户看到两个东西，不知道谁配谁」（:18）。这条**用文档就能解决**，不需要合并代码；拿它当合并的主理由，是论证结构上的错位。

正确的主理由应该是：**痛点 A + 痛点 C 都要求「一份东西同时是判据和约束」，而按载体切分做不到这一点**。这个理由在文中是存在的（散在 :14 与 :39），只是没有被摆到 §1 的标题位置。

**这不是阻断**：方向对，理由的排序错。但 §1 需要重写，否则后续评审会反复在「改文档不就行了」上打转——而这个问题本来有答案。

### 2.2 有没有更简单的做法被漏掉

有三个，逐个评估（这是判「阻断缺陷 3」的唯一依据）：

| 候选 | 解决痛点 A | 解决痛点 B | 解决痛点 C | 结论 |
|---|---|---|---|---|
| (a) 只改文档：README 互指 + SKILL.md 写明与 gate 的关系 | ❌ 仍要手动复制 | ✅ | ❌ | 缺 A、C |
| (b) 只把常驻纪律加进现有 `dsh-stage-gate`（它已在 profile 全局），skill 不动 | ❌ | ✅（段里写明） | ✅ | 缺 A，且仍是两个载体 |
| (c) `plugin-kit` 单独发一个小包（只注册 provider） | ✅ | ❌ | ❌ | 缺 B、C，且变成两个包 |
| **合并（设计所选）** | ✅ | ✅ | ✅ | 覆盖三项 |

三个更小方案**每个都缺一个目标**。所以合并不是「偷懒的大方案」，而是覆盖三项的最小载体。**阻断缺陷 3 不成立。**

需要补一句的是：设计从未写出这张表。§九「明确不做的」列了四条，但**没有一条是「被评估后否决的更小方案」**，全是范围外的事。建议把上表搬进 §1——这是设计文档最该有的那段，恰好缺了。

至于 `ctx.skills.register(skill)`（FACTS M2）：它确实更简单（直接给 `content`，可能绕开 candidate 校验、目录扫描、`resourceBase`），事实包 §九 也自认「`register` 更简单但没验证」。但 `plugin-kit` 是 4 份 references + scripts + assets 的目录型技能，`register` 的内联 `content` 模型要装下这些就得自己发明引用机制。**事实不足，不判阻断，记 §6-4。**

### 2.3 合并带来的新问题（设计都没写）

1. **作用域膨胀**。`dsh-stage-gate` 全局生效是它的设计前提；skill 却是**逐项目**资产（:14）。合并后，装一次包 = 每个项目都能看到 `plugin-kit` skill + 每个会话都注入一段「你在做 DSH 插件开发」。设计里没有任何门控（:159-170 的文本是无条件的，`assemble()` 也不看项目）。→ I1。
2. **发布耦合**。§1 把「版本天然同步」当纯收益（:29），代价没写：改一行判据 = 发一个 npm 版本 + 每个装了的人重装。这正是 §七 要保留开发版的原因，而开发版又带回漂移。**合并消掉了「两个名字」，换来「同名两源」**——见第 4 条。
3. **一次安装同时授予说服力与拦截权**。只想要判据、不想要 `tools/pre-execute` 拦截的人，在 npm 上没有路径（装了包就带拦截）。这使 §七 的独立副本**不是「降级路径」，而是一等交付形态**——设计的定性错了，连带测试覆盖也错了（§5）。
4. **语义遮蔽**。开发版 rank 100、包内 rank 550，跨层高层优先（FACTS §二）。在设计最常用的那个项目里，**开发版永远赢**。于是「同名」不再指示「你拿到的是哪一份」——这比原来「两个不同的名字」更难诊断。§一 抱怨的「用户看到两个东西」，合并后变成「用户看到一个名字、两个来源」。

## 3. 二、三段式的设计是否成立

三段式本身成立（三条接缝 FACTS M1/M3/§四 都给了契约，且互不抢占：注册表 / prompt / 工具钩子）。**问题不在结构，在段与段之间的三个未闭合点。**

### 3.1 三段互相干扰，三处具体

**a) 作用域不一致（I1）**：拦截是全局且可通过 Config 关闭（FACTS §六 有 schemastery Config）；常驻段是全局且无条件。`MERGE-DESIGN.md:163` 的文本第一句是事实断言——「你在做 DSH 插件开发」。在任何非插件项目里这句话是假的；模型据此执行「未过门不得写下游产物」，会**在没有门的项目里自我阻断**。这不是措辞问题，是错误指令。

**b) 与 Config 不联动（I2）**：gate 可以被关掉（Config 存在即意味着可关/可调），但段文本不读 Config，仍然宣称「不是建议，是约束」（:163）。关掉拦截后，段变成一个**无法兑现的承诺**：模型自我约束，代码不兜底。三段里唯一有权知道「门还在不在」的是拦截段，但它和 prompt 段没有共享状态。

**c) 名字遮蔽导致指针可能悬空（§2.3-4）**：段说「门的判据在 plugin-kit skill 里」（:165），而 `plugin-kit` 这个名字**可被项目覆盖**（§六 :198-206 明确把它当优点）。一旦项目里放的是旧版/改写版，段指向的内容与段的断言不一致，而**没有任何机制能发现**。

### 3.2 「光注册 skill 不够，必须加常驻注入」这条对我们成立吗

分三层，结论是「成立，但被夸大成必要条件」：

1. **论断本身可迁移**。FACTS §五 的原文讲的是宿主目录的**可见性语义**：`<available_skills>` 只有 name + description，模型没有任何standing instruction 去加载。这是宿主性质，不是 superpowers 的私有处境。**所以依据成立（阻断缺陷 2 不成立）。**
2. **但「必须」是设计者加的强度**。参照实现选择注入 skill 全文，是因为它 15 个 skill 都短、且它的痛点是「没人告诉模型有这些 skill」。我们的痛点 C 是「模型知道有，但不去看」——指针式注入确实对症，但事实包里**没有任何证据表明常驻注入能改变行为**（FACTS §九 也没把这条列为已核实）。设计却写成「设计上的必要条件，不是可选项」（:49）。
3. **§八 把这条验成了存在性**：「真机：启动即有常驻纪律 → 看 systemPrompt 里有没有那一段」（:227）。这只证明字符串进去了，不证明模型行为变了。**一个自称必要条件的设计，验证只做到「存在」**——这是 I6 的另一半。

建议：把措辞从「必要条件」降为「强先验 + 一个待验证的效果假设」，并在 §八 加一条可观察判据（例如同一任务在注入/不注入两次运行中，是否在写下游产物前先加载 skill）。

### 3.3 那 10 行文本与 skill 正文的关系

**会不会冲突：无法判断**——FACTS §六 只给了「SKILL.md 107 行 + 4 份 references（process/reviewer/tools/evidence）」，没有正文或大纲。按边界记 §6-1，不判 FAIL。

**会不会重复：会，而且重复的位置不对。** 可判断的部分：

- 那段文本（:162-168）三条里有两条是**门规则**（每阶段结束必须过门、被拦住不要自己造门）——这两条**已经由 `tools/pre-execute` 机械执行**（:174 拦截段保持不变）。给一个已经被代码强制的规则再加一段 prompt，边际收益接近零。
- 真正**没有强制力**的那件事——「去加载判据」——只占一行（:165）。

也就是说：**常驻段把篇幅花在了已经不需要说服的地方，把最需要说服的地方写成了一句指向。** 这与它自己引用的依据（「模型没有 standing instruction 去 consult 它们」，FACTS §五）恰好错位：依据说的是「consult」缺失，注入的却是「enforcement」的重述。

同时它构成规则的**第三份副本**：`lib/gate.js`（代码）/ `SKILL.md`（判据）/ prompt 段（散文）。三份之间没有任何对齐机制，改一处不会提醒另外两处。→ I5。修法不是删句子，而是**指定唯一权威源**：P0→P1 的细节只留在 SKILL.md（或 gate.js 的拦截消息里），prompt 段只保留「先加载 plugin-kit」+「门不可绕过，被拦就找人」。

### 3.4 §4 的代码层问题

| 位置 | 问题 | 依据 |
|---|---|---|
| :146-153 | `text()` 首帧返回空串并异步 `assemble()`。若 `text` 每会话只调一次，纪律**永不出现**；若每步调用，则第 1 步（模型决定做什么的那一步）没有纪律 | FACTS §九 明确：调用频率未核实。**这是设计自造的风险**——见下一行 |
| :159-170 | 段内容是**固定的一段文字**（约 9 行，无变量），却用 `assemble()` 异步读文件。既然是常量，直接 `const` 即可：无空帧、无需 `fs`、不触发 K2 | 内部矛盾 |
| :105 | `inject` 含 `workingDirectory`，但 §4 两段代码都没读它 | I1 的另一半证据：门控意图存在，实现里丢了 |
| :140 | `order: 121` 无理由；§六 为 rank 550 写了半页论证，order 却一个数字带过 | 缺 §6-5 |

### 3.5 §十 的命名规则自相矛盾（I7）

`:244` 说「`package.json` 的 `name`、`cordis.patch.yml` 的行 `id`、`index.js` 的 `export const name`、`candidate.provider`——这四处必须一致」，但 `:243` 的表格里 `package.json` 的 name 是 `@wufeng0105/dsh-plugin-kit`（带 scope），其余是 `plugin-kit`。**照 :244 实施，包名就得写成 `plugin-kit`，而那不是他能发布的 scope。**

事实包的约束只有一条（FACTS §三）：`provider` 必须等于注册的 provider 名，否则 validateCandidate 抛。所以正确的表述是「**三处**必须一致（插件 `name` = `candidate.provider` = `registerProvider` 的 provider 名），包名可以不同」。同时 §十 整节没有迁移：旧包 `@wufeng0105/dsh-stage-gate` 的行 id 变了，已装的人更新后是两条并存还是一个都不生效？台账（FACTS §六 有 13 条测试的 `lib/ledger.js`）的存储位置是否带插件名？→ 设计缺「改名迁移」一节。

（`:244` 那句「与 skill 同名，但一个是包名一个是行名，不冲突」本身也不准：`plugin-kit` 既是插件 name 又是 skill name 又是 `candidate.provider`，三者同名在这里恰好无害，但这句话把「包名」和「行名」当成两个维度，掩盖了真正的三处一致约束。）

## 4. 三、五个坑的应对是否充分

先对齐集合。**设计的「五个坑」与事实包的「五个坑」不是同一组**：

| 事实包 §四 | 设计 §5 | 是否覆盖 | 评价 |
|---|---|---|---|
| K1 disposer 不属本 fiber | #1 | ✅ | 应对完整（`ctx.effect` 包裹），代码 :107-120 也是对的 |
| K2 读未 inject 的服务会**抛** | #2 | ✅ | 原则对，但 §4 代码里**看不到 try/catch 的落点**；且若按 §3.4 改用常量文本，这条对第一段就失效，只剩 `list()` 里的路径探测需要它 |
| K3 候选形状错**穿透注册表**抛 | #3 | ⚠️ 部分 | 「读不到就 skip」只防住了 **IO 失败**；K3 说的是**构造出来但字段违规**（provider 不等、name 不合语法、description 空）——那不走 IO 路径。必须「返回前本地逐字段校验，不合法就丢弃 + warn」，而不是「读不到就 skip」 |
| K4 name 不合语法静默跳过 | #5 | ✅ | 正则校验 + 丢弃，充分 |
| **K5 模块顶层不能抛：`apply()` 还没跑，顶层抛会把整个 server 带下去** | **无** | ❌ **丢了** | 这是既有真坑、有源码位置（`:36-41`）、后果最重（不是 skill 坏了，是**整个 server 起不来**）。§5 的表里没有它，§三 的结构里也没有对应的模块顶层约束。**必须补回** |
| （事实包 §三 的 500 截断，属渲染约束不是「坑」） | #4 | 由此顶替 | 见下 |

**因此「五条应对是否充分」的答案是：4 条到位、1 条部分、1 条缺失、1 条顶替。**

- **K4 顶替了 K5（N1/N4）**：设计把「description 超 500」塞进了 K4 的位置，把「name 不合语法」挤到 #5，于是事实包的 K5 掉了出去。更要紧的是**这条坑的立论与事实包冲突**：设计说「我们在 plugin-kit 上已经踩过：654 字符被截断」（:186），FACTS §六 的实测是「431 字符（上限 500，安全）」。合理的解释是 654 是历史、431 是修复后——但设计没写「已修复，需回归」，读者无法区分「现在仍危险」和「曾经危险」。而「打包前检查长度」的正确定位是**回归测试**（431→654 只要一次编辑，且截断是渲染期静默发生的），不是「待解决的坑」。
- **遗漏的坑（只基于事实包能说的）**：除 K5 外，还有一条**事实包给了材料、两份文档都没列为坑**的：**rank 遮蔽导致验证失真**。FACTS §二 给了 rank 表与跨层优先，FACTS §六 说 `plugin-kit` 的独立副本就在 `.dsh/skills/`（rank 100），设计 §八 的真机验证判据是「装上后 skill 出现在目录」。在开发项目里这个判据**必然通过——通过的是开发版，不是包内版**。这是设计里最危险的一条：验证会给出假绿，而且是在唯一会做验证的那个环境里。→ I3。

## 5. 四、保留独立版本的决定

### 5.1 决定本身合理，但定性错了

保留 `.dsh/skills/plugin-kit/` 是对的，理由比 §七 写的更强：**装了 npm 包就必然带 `tools/pre-execute` 拦截**（§九 不做设置页，`client.js` 不做），所以「只要判据、不要强制力」的人在 npm 上**没有路径**。独立副本不是「降级路径」，是**唯一能提供纯判据的渠道**。

定性错了的后果很具体：§八 的验证表里，独立副本**一条验收都没有**；它被当成「出问题时才用」的东西，实际上它是**一等交付形态**。要么给它验收，要么明确写「best-effort，不保证与包内同步」。

### 5.2 「两份可能漂移」的缓解不够——不够的理由是可证的

§七 的缓解只有一句 README 提醒（:218）。事实级反驳：

1. **开发项目里永远看不到包内版**。rank 100 vs 550，跨层高层优先（FACTS §二），设计自己的表也写了「100 项目 `.dsh/skills` 能覆盖我们 ✅」（:198）。所以在唯一会改判据的地方，**包内副本从不被执行**。
2. **漂移不可观测**。两棵树不同步时，没有任何测试会红；模型拿到的仍是开发版，行为正常。漂移只会在「别人装包」时暴露——最晚、最贵的时刻。
3. **§八 会给出假绿**（见 §4 末）。README 提醒救不了假绿。

所以：**README 是文档级缓解，面对的是可观测性缺陷。层级不对。**

### 5.3 更好的做法（按代价排序）

| 方案 | 做法 | 代价 | 适用 |
|---|---|---|---|
| **A（推荐）** | 指定 `.dsh/skills/plugin-kit` 为**唯一权威源**，包内 `skills/` 是构建产物：加 `sync` 脚本；在 `test/skill-provider.test.mjs` 里断言两棵树**文件树哈希相等**（这条测试已经在 §三 的计划里，只是没给它这个职责） | 一个脚本 + 一条断言 | 想继续维护两份 |
| **B** | 不维护两份：开发时用 `pnpm link` / `npm pack` 直接对着安装态改 | 改一次要重装一次 | 只服务装包用户 |
| **C** | 独立副本降级为「快照」：文件名/首行写明版本与生成时间，README 声明「此处可能落后，以包内为准」，并把 §八 的验收范围明确排除它 | 几乎零 | 明确它只是给人看流程用的 |

三个都比 README 强。**A 最贴合设计意图**（它已经打算写 `skill-provider.test.mjs`，加一条哈希断言是顺手的事）。
