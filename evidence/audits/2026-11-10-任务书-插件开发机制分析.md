# 任务书：DSH 插件开发全过程的机制分析（分析阶段）

给新会话执行者：你是一次独立分析的分析者。作者的处境在 §1；要读的材料在 §2；要回答的问题在 §3；交付形式在 §4；硬约束在 §5。本次只做分析与机制建议，不做任何实现。

## 1. 作者的处境（只写事实与诉求）

作者用「随意许愿式」的方式开发过三个 DSH 插件（当前目录下的三个仓），功能都跑通并已发布。事后作者有三件在意的事：

1. 不确定开发过程是否遵循了 DSH 的原生方式。在意的原因之一：宿主可能已经内置了某些能力，自己重造是浪费。
2. 开发推进中，AI 会逐渐不再遵守 skill 里的约定——上下文越积越多，或早期决定形成路径依赖，最后用的不是当初约定的做法。
3. 开发结束之后还有两件事没有稳定做法：
   - 发版：插件怎么正式发布出去；
   - DSH 本体更新后的兼容性：插件依赖的宿主接触点是否仍成立；不成立时，要能检测出具体哪些点失效了、该怎么调整。

作者反复的经历：同一批要求，需要一次次向 AI 强调。

作者想要的：一套机制，让现有 skill 的内容在它该用的时刻自动起作用，而不是靠一次次强调。本次先要分析和机制建议；可执行设计等作者确认方向后另行讨论。

每个仓要能说清：

## 3. 要回答的五个问题

**Q1 阶段**：一个 DSH 插件从想法到退役，客观上要经过哪些阶段？从三个仓的现状、skill 的分工、宿主的机制推导，不套用任何现成流程模板。

**Q2 痛点**：每个阶段里，作者会遇到什么痛点和困境？每条必须给证据——某个仓里的某个结构、某份 skill 里的某条要求、宿主的某个机制——引用到具体文件。

**Q3 覆盖**：现有 skill 分别覆盖了哪些阶段的哪些问题？哪些阶段或问题没有任何 skill 覆盖？给出映射表。

**Q4 遵守**：开发过程中，有哪些真实存在的机制能把约定在「该用的时刻」送到执行者面前？逐个说明：绑定在什么时刻、为什么那个时刻必然发生、能覆盖什么、边界在哪。机制必须是 DSH 环境里真实存在的——你体验到的、探测到的、或 skill 写明的；不要发明理想化的机制。

**Q5 机制**：综合以上，给作者提出这套机制的建议形态——由哪几部分组成、每部分绑在哪个时刻、为什么这个形态能减少作者「一次次强调」。只到建议形态为止，不写实现。

## 4. 交付形式

分三层，按序交付：

1. **分析**（Q1–Q4）：表格为主，每条结论可指回文件路径、一次探测调用、或 skill 原文。
2. **机制建议**（Q5）：只给形态与绑定点，不写实现。
3. **你要问作者的问题**：鼓励在开读前列出（最多 5 个，问完等答案再继续）；分析过程中出现新的关键分叉也可以再问。

读不完、测不到的，写 UNVERIFIED 并说明原因。UNVERIFIED 是合法交付，不许用推测补齐。
