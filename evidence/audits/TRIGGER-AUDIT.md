## 重要缺陷

**I1 原则 3 的引文是撤回版，"没人提供强制力"与自家文档冲突。**

依据：现行原则 3 的原文是「判据文本 → skill；强制力 → `AGENTS.md`（短规则常驻）+ 人工开门」，并明确注明「上一版写「不该再加 skill」过绝对了，已修正」（[SKILL-LAYERING-DESIGN.md:168-177](SKILL-LAYERING-DESIGN.md#L168-L177)）。计划引的那句在该文件中**零出现**——`缺执行` 在该文件出现 0 次，在 TRIGGER-PLAN.md 出现 2 次（第 35 行引文、第 174 行自述）；SKILL-LAYERING-DESIGN.md 里只有 §9 的「缺知识」（2 处）/「缺程序」（2 处），而那句的结论是「缺程序才建 skill」，不是「缺执行→建机制」。因此 1.2 表格判「触发/强制没人提供」（[TRIGGER-PLAN.md:25-29](TRIGGER-PLAN.md#L25-L29)）与自家文档直接冲突：强制力有归属，只是归属在 AGENTS.md + 人工开门。

影响：第二步的设计前提建立在撤回版引文上；同时漏掉与 AGENTS.md 层的关系（见 I4）。真正要论证的命题更窄也更硬——**"已有的强制力在执行可靠性上不够"**，而不是"没有强制力"。

**I2 G3 在 H1–H14 下没有落点，第二步出口判据对它不可满足。**

依据：G3 要求"跳过门被记录成可审计事件"（[TRIGGER-PLAN.md:49](TRIGGER-PLAN.md#L49)）。H1–H14 中 H9 `session/event` 是 emit、post-commit、fire-and-forget 的**观测**接口；没有任何一条是"向会话日志追加事件"。

唯一的近似是 H13 `agent.inject()`：注入的内容会进入会话记录，因此能留下痕迹。但它是一条**消息**，不是一条**事件**——它占用后续每一步的上下文预算，混在对话流里，不能被"按类型查询"，也无法在 agent 空闲时写入。把它当台账用，等于用对话记录当审计日志。

影响：第二步出口判据"每个目标都能指到具体接缝 + 具体事件"（[TRIGGER-PLAN.md:110](TRIGGER-PLAN.md#L110)）对 G3 不可满足。第二步会在这里卡住，或者被静默降级为"插件自己写个文件"——而计划没有授权这个降级，也没定义谁读那个文件、怎么算"可审计"。

**I3 G1 只验"指令出现"，不验"指令被采纳"；最可能的失败模式没有预案。**

依据：G1 判据是"审查指令自动出现在下一 step"（[TRIGGER-PLAN.md:47](TRIGGER-PLAN.md#L47)），不要求模型执行。注入文本与 AGENTS.md 里那句在性质上相同：都是提示，不是强制。风险表（[TRIGGER-PLAN.md:171-177](TRIGGER-PLAN.md#L171-L177)）没有"注入被忽略"这一行，尽管第二步第 5 项提到了它。

影响：G1 可以在"模型完全忽略"的情况下通过验收，用户原痛点从"人忘了说 → 门不存在"变成"模型没理 → 门仍然不存在"。这是本计划最可能的失败模式，却没有判据、没有预案、没有观测点。

**I4 五步不含部署；AGENTS.md 里旧的手工触发句无人处置。**

依据：交付物清单（[TRIGGER-PLAN.md:187-196](TRIGGER-PLAN.md#L187-L196)）止于"skill 回写 + ROADMAP 更新"；第四步只在一次性 profile 里装、验、拆（[:134](TRIGGER-PLAN.md#L134)）。没有任何一步把插件装进日常 profile，也没有一步处置 AGENTS.md 现有的触发句。

影响：五步走完，用户在日常会话里拿不到触发器。旧的触发句若保留，会出现"插件提醒 + 人再提醒"的双触发；若删除，没装插件时连提醒都没有。第二步要求"有一套插件不在时的降级行为"，而这条降级路径实际落在 AGENTS.md 上——却没有任何步骤拥有它。

**I5 事实包第六节自称"所需事实全部在 H1–H14"，实际至少缺三项。**

依据：[INTERFACE-FACTS.md:69](INTERFACE-FACTS.md#L69) 称"判断这条主张需要的事实，全部在上表 H1–H14"。实际缺四项：跨会话状态怎么持久化（F1，H14 是 per-session）、插件能否/如何读工作区里的阶段产物（F2）、运行期怎么拿到 skill 里的判据文本（F3）、`dsh-agent-instructions` 能否复用（F5）。前三项决定状态机与第二步第 3 项怎么写，第四项决定"新建插件"是否必要。

影响：这句话让审计员以为不必再问，第二步会在入口处卡住；它也是"该新建插件"这一步无法被证伪的原因。这是本次只能给 PWC 而不能给 PASS 的直接原因。

## 次要缺陷

**M1**「不是边界，是错层」（[TRIGGER-PLAN.md:5](TRIGGER-PLAN.md#L5)）二分过强。它确实是 skill 层的边界，正因为是边界才需要换层；两者不互斥。写成"是 skill 层的边界，因此在别的层属于错层"更准，也避免下一步推理滑成"凡边界都该建插件"。

**M2** G1 判据"不输入任何指令"有歧义：用户必然要给初始任务，应写成"不额外输入开门指令"。另外未区分"agent 自己写产物"与"人或外部进程写产物"——后者不产生 step，而 H13 不唤醒 agent，G1 不成立。

**M3** 三个接缝选型陷阱没有写进设计约束：H3 `restrict` 是静态 allow/deny 列表，只能移除工具、不能带理由、不能随状态变，拿它做 G2 会得到"没有理由、粒度是工具名"的拦截；H2 `guard` 是同步、不能 await，判定若要读盘就只能改走 H1，且 H1 要求观察 `exec.signal`；H13 不唤醒 agent。第二步第 4 项应显式写"选 H1 还是 H2"，并接受它对状态存放位置的反向约束。

**M4** 第三步"接线可达性：内核被产品代码 import"太弱：import 了但没挂到任何宿主事件上也算过。应改为"内核被某个宿主事件触发，且有一条端到端离线用例"。

**M5** 第四步逃生口没有下限："拿不到 L1 的项，写明无法验证 + 原因 + 谁接受"（[:139](TRIGGER-PLAN.md#L139)）允许三项全部 UNVERIFIABLE 仍满足字面判据。应设最低条数，例如 G2 必须有 L1。

**M6** 第五步"skill 里不出现空头承诺"是语义判断，不可机械核验，应改成可 grep 的句式清单。另外 skill 引用一个外部插件属于新的层间耦合，原则 5 只规定了"自建 → 内置"的单向关联，没有覆盖"自建 → 外部插件"。

**M7** L1/L2/L3 在事实包里只有"L2 = 真机 inspect、L3 = 读源码"和一句"没有运行时行为证据（L1）"（[INTERFACE-FACTS.md:5](INTERFACE-FACTS.md#L5)、[:51](INTERFACE-FACTS.md#L51)），没有 L1 的定义与采集方法，而第四步判据直接使用 L1。

## 缺什么事实

- **F1 跨会话状态持久化**：阶段状态存在哪、重启/新会话怎么读回。H14 是 per-session 派生，不够。
- **F2 插件对工作区的读写权限与惯例**：能否直接读阶段产物目录、有没有推荐的存放位置。
- **F3 运行期获取 skill 文本的方式**：读文件？路径从哪来？还是只能内置模板（那就违反"判据留在 skill、插件只读不复制"）。
- **F4 是否存在向会话日志追加事件的接缝**：决定 G3 能否按"事件"实现。
- **F5 `dsh-agent-instructions` 是否可配置/可复用为通用的"文件改动 → 注入"规则**：决定"新建插件"是否必要，直接影响阻断类型 3 的判定。
- **F6 H1 的 `ask` 决策被用户解决后是否留痕、插件能否观察**：这是"手动放行"最可能的审计落点。
- **F7 L1 的定义、采集方式与最小样本**。

## 一、接缝是否足以支撑目标

| 目标 | 主接缝 | 类型够不够 | 判定 |
|---|---|---|---|
| **G1** 落盘后自动触发 | H9 `session/event`（step/end）或 H10 `tools/result` 取路径 → H11 `agent/pre-step` 注入 `decision.messages` | 感知用 emit 足够；注入必须 waterfall，H11 是 | ✅ 可做，与 `dsh-agent-instructions` 同构（[INTERFACE-FACTS.md:28-36](INTERFACE-FACTS.md#L28-L36)） |
| **G2** 未过门时拦截 | H1 `tools/pre-execute`（`deny{reason,info}`）/ H2 `tools.guard`（同步返回理由）/ H4–H5 `fs/*-intent`（单槽 waterfall） | 拦截需要同步或 waterfall；H1/H2/H4/H5 都满足 | ✅ 可做，但"标记阶段完成"必须先绑定成具体操作 |
| **G3** 跳过可审计 | 无 | H9 是 emit 观测，不是追加；H1–H14 没有写会话日志的接缝 | ❌ 按"会话事件"做不到；改为插件自有台账才可行 |

**类型冲突：没有硬冲突。** 但有四个具体陷阱，都会让设计"看起来接上了、实际不对"：

1. **H4/H5 是写前意图，不是落盘后。** `fs/write-intent` 在写文件之前触发，文件还没写成。若把 G1 映射到 H4/H5，注入会发生在半成品时刻，审查员看到的是未完成的产物。G1 的"落盘后"只能用 H9 的 post-commit 或 H10 的 `tools/result`。**这是时序错配，不是类型错配，但后果一样。**
2. **H3 不能承担 G2。** `restrict` 是静态 allow/deny 列表，只能移除工具，不能带理由、不能随状态变。G2 判据要求"deny 并给出理由"，H3 给不了。它只能做粗粒度的能力开关。
3. **H2 同步 → 状态必须常驻内存。** `ToolGuard` 返回 `string | undefined`，不能 await。若拦截判定要读盘或查台账，H2 用不了，只能走 H1；而 H1 要求异步门观察 `exec.signal`。这个约束会反过来决定状态机放在内存还是日志里。
4. **H13 不唤醒 agent。** 它只能保证"下一步带上"，不能"空闲时拉起"。G1 判据写的是"下一 step"，不冲突；但若产物由人或外部进程写入，就没有 step 可注入，G1 不成立。

**结论**：G1、G2 有接缝；G3 没有。事实包第六节说"若这些接缝不足以做到『感知落盘 → 注入 → 拦截』，主张就要修正"——这句话对 G1/G2 不触发，对 G3 触发。计划应把 G3 从"事件"改为"台账"，并补 F4 确认。

## 二、原则推论是否成立

### 2.1 引文核验

| 项 | 内容 |
|---|---|
| 计划引用的"原则 3" | 「缺知识 → 建 skill；缺执行 → 建机制，不是再加 skill」（[TRIGGER-PLAN.md:35](TRIGGER-PLAN.md#L35)） |
| 文档里实际的原则 3 | 「判据文本 → skill；**强制力 → `AGENTS.md`（短规则常驻）+ 人工开门**」，并注明"上一版写「不该再加 skill」过绝对了，已修正"（[SKILL-LAYERING-DESIGN.md:168-177](SKILL-LAYERING-DESIGN.md#L168-L177)） |
| 核验结果 | `缺执行` 在 SKILL-LAYERING-DESIGN.md 中 **0 次**，在 TRIGGER-PLAN.md 中 2 次；该文件只有「缺知识」（2 次）/「缺程序」（2 次），且结论是"缺程序才建 skill" |

也就是说：**作者认的那个错，现行文档里已经改过了。** 现行原则 3 并没有把"触发"判给 skill，它判给了 AGENTS.md + 人工开门。计划拿改前的版本当依据，去论证一个改后的文档并没有主张的东西。

### 2.2 推论成立吗

分三步：

- **"skill 做不到自动触发"——成立。** 事实包第三节的判断是对的：skill 是文本，没有执行环境，不能监听、不能拦截。
- **"所以这是机制层的事"——成立。** 这是本次自我修正里真正对的部分。
- **"所以该做成插件"——这一步没有论证。** 插件是机制层里最重的一种实现。同一层里还有：AGENTS.md 写法强化、`ctx.systemPrompt.section` 挂常驻短规则（H12）、`ctx.tools.guard` 单点同步守卫、复用 `dsh-agent-instructions`。计划一个都没对照。

真正该论证的命题不是"没人提供强制力"，而是：**"已有的强制力（AGENTS.md + 人工开门）在执行可靠性上不够。"** 这个命题更窄、更容易证（用户原话就是"同一批要求要一次次强调"），也更难被"你自己文档里写了 AGENTS.md"反驳。

建议把 1.2 表格改成三行：

| 层 | 现状 |
|---|---|
| 判据文本 | skill 有 ✅ |
| 常驻规则 | AGENTS.md 有，但**概率性遵守** ⚠️ |
| 确定性拦截 | 无 ❌ |

这样"缺"的只有第三行，而第三行正好对应 G2。计划的说服力会强得多，也不会再和自家文档打架。

### 2.3 自我修正是对是错

**不是从一个错跳到另一个错；是"错因改对了一半，依据用了撤回版"。**

- 原判"skill 做不到"：作为对 skill 层的陈述为真，但把它当成"能力边界"是**判死**，这是错的。
- 新判"不是边界，是错层"：方向对（能力存在，只是不在这一层），但"不是边界"过强——它就是 skill 层的边界，所以才是错层（M1）。
- 新判隐含的"所以该做成插件"：**跳步**。层归属不等于实现形态，更不等于新建插件。
- 自述"我在第 5 条上犯了同样的错——把触发当成 skill 该写的内容"：与现行文档不符。文档没有把触发判给 skill。

## 三、计划是否可执行

### 3.1 五步顺序

顺序本身合理：审计 → 设计 → 实现 → 运行时 → 回写。缺两个环节：

- **复用评估**（应在第一步与第二步之间）：F5 没答之前，"新建插件"与"配置现成插件"是两条并列路线，而计划直接进了后者。
- **部署**（应在第五步之后，或明确声明不在范围内）：见 I4。

另有一处前置依赖被忽略：第二步的六项里有三项（状态机、注入文本、拦截规则）依赖 F1/F2/F3，事实包没给，所以第二步会在入口处卡一次。

### 3.2 出口判据能不能判真假

| 步 | 判据 | 能判真假 | 问题 |
|---|---|---|---|
| 1 | PASS/PWC 进；FAIL 停；缺事实补后重审一次；2 轮上限 | ✅ | 无，这一组是全文最硬的 |
| 2 | 每目标指到接缝 + 事件；每接缝标证据等级；有降级行为 | ⚠️ 部分 | 对 G3 **不可满足**（无接缝可指），第二步会卡住或被迫静默降级 |
| 3 | 语法过、测试绿、一条变红、内核被 import | ⚠️ 部分 | "被 import" 太弱，import 了不接线也过（M4） |
| 4 | G1/G2/G3 各一条 L1；日常 profile 未动；拿不到写 UNVERIFIABLE | ⚠️ 部分 | 逃生口无下限，三项全 UNVERIFIABLE 也满足字面（M5）；L1 无定义（M7） |
| 5 | 无空头承诺；符合原则 1 | ⚠️ 部分 | "空头承诺"不可机械判定（M6） |

### 3.3 第二步六项够不够

**够写骨架，不够判"做对了"。** 第三步的出口判据是语法、测试、import——一个玩具状态机也能全过。真正决定成败的语义，六项里没有：

1. 状态持久化与并发（多会话同仓时谁的阶段状态算数）——F1
2. 误拦的恢复与例外通道（G2 会 deny 写文件；状态判错就会把正常写作挡死，怎么退出来）
3. 注入被忽略的检测（怎么知道提醒没被采纳）——I3
4. 部署与开关所有权（谁装、默认开还是关、怎么关；风险表最后一行只说"加开关"，没说默认值）
5. 拦截接缝选型及其反向约束（H1 vs H2，见 M3）

建议在第二步加两项"可执行语义"：**状态转移表**（每个状态 × 每个事件的下一状态）和**拦截规则的输入输出样例**（给定状态 + 工具调用 → 期望决策）。没有这两样，第三步的"变红证明"只能证明代码会跑，不能证明判断对。

### 3.4 风险与预案覆盖

覆盖了"做不成"（接缝不足、装不上、注入有坑、太侵入），没覆盖另外三类：

| 缺的风险 | 为什么会发生 | 建议预案 |
|---|---|---|
| **做成了没用**：注入被忽略 | 注入是提示，与 AGENTS.md 同性质 | 在 G1 判据里加"下一 step 是否真的执行了审查"；或明确 G1 只承诺"提醒到达"，强制交给 G2 |
| **做成了碍事**：误拦 | 状态判错 / 多会话串状态 → deny 正常写作 | 定义例外通道与恢复命令；deny 的 reason 必须包含"怎么解除" |
| **做完没装上**：部署缺失 | 第四步是"装→验→拆" | 加第六步，或明确写"本计划交付到可验证为止，部署另立" |
| **多会话互相踩** | 同一仓库两个会话，H14 是 per-session | 状态落点必须显式选：会话级 or 仓库级 |

### 3.5 一条更轻的路线

不是阻断，但值得在第二步之前考虑：

- **G2 优先，G1 降级。** G2 是唯一把"概率性遵守"换成"确定性拦截"的目标；G1 只是把提醒换个位置，模型仍可忽略。若只能做一个，做 G2——风险面、实现量、验证成本都小一个量级。
- **用目录约定替代"读 skill 判据"。** 若阶段产物按 `stages/<n>/…` 落盘，拦截规则可以是"没有第 n−1 门记录时，deny 对 `stages/<n>/` 的写"。这绕开了 F3 的循环（插件读不到 skill 文本 → 只能内置模板 → 违反"不复制判据"），把第二步第 1/3 项从"读判据"降为"读目录"。
- **H12 提供"不动 AGENTS.md 的常驻规则"。** 插件可用 `ctx.systemPrompt.section` 挂一条短规则，不必改 AGENTS.md；但它只在插件装了才生效，所以 AGENTS.md 仍要留作降级。
