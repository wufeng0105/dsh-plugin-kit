# 第二轮审计：阶段门触发器设计（G2 + G3）

> 审计对象：[TRIGGER-DESIGN.md](TRIGGER-DESIGN.md)（**240 行版本**，mtime 2026-11-09 12:26:16）
> 参照：[INTERFACE-FACTS.md](INTERFACE-FACTS.md)、[TRIGGER-PLAN.md](TRIGGER-PLAN.md)、[TRIGGER-AUDIT.md](TRIGGER-AUDIT.md)、[REVIEW-01-trigger.md](REVIEW-01-trigger.md)（§4.0 引用了它）
> 未读：`app.asar` 源码、`docs/repos/`、`impl/`、`plugin-kit` 的 skill 文件。
> 说明：设计文档在我审计期间从 215 行变为 240 行（新增 §4.0「渐进采用路径」）。以下行号按 240 行版本；本文只对 240 行版本负责。

## 判定

**PASS-WITH-CONDITIONS**

一句话：**接缝不用换；要换的是三处论证、补的是四类边界定义。**

- 第二节的四个否决理由我逐个核过：**没有一个错到需要重做接缝选择**。H3 那条完全成立；H4/H5 那条方向成立但压在一个事实包没有的事实上（见 C2）；H2 那条的**主因**（同步）成立，**次句**（无 `exec.arguments`）与契约不符。
- 核心决定（目录约定）作为**状态表示**成立；但它的**理由**写错了（I1）、**代价**没交代全（I2），而且这份代价正好被 §1.4 的一句绝对化断言盖住了。
- 设计能写出骨架，**不能直接写出可验收的实现**：四处语义（函数签名、路径归一化、未知 verdict、listener scope）留到实现阶段会被随机决定（M1/M2/M3/I6）。
- §5 的验证能证明「插件按预期行事」，不能证明「真的能用」——因为最可能失败的场景（真实工作根本不写进 `stages/`）不在任何一条用例里（C9）。

## 阻断缺陷（仅限三种）

**无。**

三处接近阻断的，逐条说明为什么不够格——这是本次判定最需要交代的部分：

**1. I1（F3 循环的依据是错的）够得上「依据不成立」的字面，但不改变任何选型。**

设计 §1.1 说「读 skill 判据」会死循环，理由是「skill 是否加载取决于描述匹配 → 匹配不到就没有判据」（[TRIGGER-DESIGN.md:15-19](TRIGGER-DESIGN.md#L15-L19)）。这条链在事实包里已被判「有解」：F3 写着「**有解**：H16 `ctx.skills.get(name)` 返回 `SkillDefinition.content`（全文）。插件不必复制判据，读 skill 即可」（[INTERFACE-FACTS.md:76](INTERFACE-FACTS.md#L76)），而 H16 的签名是**按名字取**（[INTERFACE-FACTS.md:27](INTERFACE-FACTS.md#L27)），不经过描述匹配。所以「读不到」不成立。

但这不是阻断，因为：**能读到全文 ≠ 能用它做判定**。判据是散文（「什么算过、三态怎么判」），代码无法评估；退一步用模型评估，会在 `tools/pre-execute` 里引入一次不可控的推理调用，判定从确定性退化为概率性——这恰好否掉 G2 的全部价值（[TRIGGER-PLAN.md:62](TRIGGER-PLAN.md#L62)）。所以「不读 skill 判据」的结论有更强、更干净的理由，「F3 死循环」只是把一个**做不到的用法**误写成**读不到的东西**。

→ 判重要、不判阻断；**但必须改**，因为它是被点名为「最关键的一个决定」的唯一依据（§1.1 第一句），实现时若有人按它解释「为什么不读 skill」，会得到错误的世界模型。

**2. I2（§1.4「静默跳过不可能」不成立）接近「核心决定错」，但机制在采用约定的项目里确实成立。**

出处：[TRIGGER-DESIGN.md:110](TRIGGER-DESIGN.md#L110)。这句话的前提是「下游产物一定写在 `stages/p<n>/`」，而设计自己规定了「不在 `stages/p<n>/` 下 → 放行（不管）」（[:139](TRIGGER-DESIGN.md#L139)），且没有任何接缝能强制工作产物进入这个目录（G1 已缓做，AGENTS.md 的旧触发句处置也不在本设计范围）。于是默认路径是：**真实工作不经过 `stages/` → 不拦、不记、无任何痕迹显示机制没生效。**

这确实是「看起来存在、实际不存在」，也是 [REVIEW-01-trigger.md:65](REVIEW-01-trigger.md#L65) 自己写下的最担心的事。为什么仍不判阻断：它**不是设计决定错**，而是**决定的作用域被说大了**。目录约定仍是同层唯一可行方案（见下方「有没有更简单的方式」），采用约定的项目里门是真的；要改的是表述 + 给「未采用」一个可观测状态，不需要推翻任何选型。

**3. 漏掉明显更简单的方案？我找了两条，都不更优。**

- **用标记文件名代替 `GATE.json`**（`stages/p0/PASS` / `SKIP`，即 [TRIGGER-PLAN.md:98](TRIGGER-PLAN.md#L98) 原方案的思路）：能消掉「可解析但 verdict 未知」和「JSON 解析失败」两个失败面，人手写也更省事。但它丢掉 `reason`/`evidence`/`at`/`by`，而这些正是 G3 要留的痕；改用文件名承载就得把元数据挪进台账，反而多一处不一致。**不构成「更简单」。**
- **用 H1 的第四态 `ask` 代替 `deny`**（[INTERFACE-FACTS.md:11](INTERFACE-FACTS.md#L11) 列了 `allow/deny/cancel/ask`，第一轮审计也把 `ask` 当作「手动放行」的候选，[TRIGGER-AUDIT.md:227](TRIGGER-AUDIT.md#L227)）：对使用者更友好，省掉手写 JSON。但它给不了 G3——插件的落点是 pre-execute，看不到审批被解决之后的结果（F6 未查，[INTERFACE-FACTS.md:82](INTERFACE-FACTS.md#L82)），台账仍然是空的。**是补充选项，不是替代方案。**

因此不构成阻断类型 3。

## 重要缺陷

### I1 核心决定的依据写错了：F3 已被事实包判「有解」，设计的死循环链不成立

**依据**：§1.1 称「审计指出这会形成死循环（F3）……skill 是否加载取决于描述匹配」（[TRIGGER-DESIGN.md:15-19](TRIGGER-DESIGN.md#L15-L19)）。事实包 F3 明写「**有解**」（[INTERFACE-FACTS.md:76](INTERFACE-FACTS.md#L76)），H16 是 `get(name)` 按名取全文（[:27](INTERFACE-FACTS.md#L27)）。第一轮审计确实用过「插件读不到 skill 文本」这个说法（[TRIGGER-AUDIT.md:206](TRIGGER-AUDIT.md#L206)），但那是在 C3 补 F1/F2/F3/F5 **之前**写的；设计在事实包补完之后仍照抄了旧前提。

**影响**：文档里最重要的一个决定，依据与自家事实包直接冲突。后果不是选型错，而是（a）下一步实现时若有人拿这条去解释设计，会得到「skill 内容拿不到」的错判，进而可能去复制判据（正好违反 §1.1 自己想守的「不复制」原则）；（b）掩盖了真正的理由——**代码不能评估散文判据**。这条理由还应该顺手回答一个设计没答的问题：为什么不把判据「编译」成机器可读规则（答案大概率是「判据会随事故演进，编译一次就僵化」，但要写出来）。

### I2 §1.4「静默跳过不可能」不成立：强制面 = 状态表示面，而没有任何东西强制工作进入这个面

**依据**：规则是「写 `stages/p<n>/` 时查前置门」（[:30](TRIGGER-DESIGN.md#L30)、[:139](TRIGGER-DESIGN.md#L139)），对照物是「静默跳过 **不可能**——不写 `GATE.json` 就写不了下游产物」（[:110](TRIGGER-DESIGN.md#L110)）。但下游产物写在哪，本设计管不到；G1 缓做（[TRIGGER-PLAN.md:89](TRIGGER-PLAN.md#L89)），skill 回写排在第五步（[TRIGGER-PLAN.md:216-227](TRIGGER-PLAN.md#L216-L227)），且在部署之后。

**影响**：设计承诺的闭环只在「项目已按约定组织」时闭合。更麻烦的是它**无痕**：不写 `stages/` 的项目连台账都没有一条「本可以拦住」，与 `enforce: false` 的 shadow 模式（[:172-176](TRIGGER-DESIGN.md#L172-L176)）无法区分——一个是「机制在观察」，一个是「机制根本没运行」，而两者在证据上完全一样。§7 的一句话「它不让你忘了开门就往下走」（[:240](TRIGGER-DESIGN.md#L240)）在默认场景下是假的。

### I3 G3 的落账触发点没有接缝：人手写 `GATE.json` 不产生工具调用，写前观察也确认不了写入成功

**依据**：§1.4 的四行都写成事件式——「审查员写 `GATE.json` → 台账记 skipped:false」「**人写** `GATE.json` → 台账记 who: human」「人写 skip → 台账记 skipped: true」（[:105-112](TRIGGER-DESIGN.md#L105-L112)）。但插件唯一的观察点是 H1 `tools/pre-execute`，它只看到**工具调用**，且发生在写入**之前**。人在编辑器里写文件、外部进程写文件，都不产生工具调用；写前观察也无法确认这次写真的落盘了。§3.2 另给了一条路——读到 skip 时「记一行 warn」（[:145](TRIGGER-DESIGN.md#L145)）——那是**读时补记**，语义完全不同：没被下游写触发过的门永远不入账，`who` 无从判定。

**影响**：G3 是本次两个目标之一，它的核心场景恰好是「人跳过门」。按现设计，这个场景要么不入账，要么记成「意图」。台账里 `who: "agent | human"`（[:85](TRIGGER-DESIGN.md#L85)）这个字段没有任何接缝能可靠填充——要么删掉，要么标 `unknown`，要么补 F6。

### I4 「约定」本身没有定义完整：`GATE.json` 字段集、`p<n>` 与九张阶段卡的对应关系、谁改 skill

**依据**：全文只规定了台账记录格式（[:80-90](TRIGGER-DESIGN.md#L80-L90)），**没有规定 `GATE.json` 的字段集**——只说查 `verdict`（[:30](TRIGGER-DESIGN.md#L30)）、举例 `by=human`（[:108](TRIGGER-DESIGN.md#L108)）、台账里还有 `evidence`/`reason`/`at`（[:87-88](TRIGGER-DESIGN.md#L87-L88)）。谁按什么格式写这个文件、哪些字段必填，没写。另外 `plugin-kit` 是「9 张阶段卡」（[TRIGGER-PLAN.md:11](TRIGGER-PLAN.md#L11)），设计只列到 `p2` 加省略号（[:23-28](TRIGGER-DESIGN.md#L23-L28)），**没有说 `p<n>` 与这九张卡如何一一对应、由谁负责把 skill 改成这套编号**。

**影响**：这是设计阶段的合同缺口，不是实现细节。审查员（一个 agent）要按 `GATE.json` 写门，格式靠猜；`p0..p8` 与卡片的映射一旦错位，产物会写进错误的阶段目录，门就查错了对象——而且不会报错，只会静默放行或误拦。第五步的回写如果只写「描述行为、不写实现」（[TRIGGER-PLAN.md:221](TRIGGER-PLAN.md#L221)），这套编号约定就没有归属。

### I5 写通道是按工具名枚举的，而 H1 是开放集合：未枚举的写工具无声绕过，验证计划也发现不了

**依据**：§1.2 声称 H1「能覆盖所有写通道（write / edit / bash 重定向）」（[:48](TRIGGER-DESIGN.md#L48)），但 `extractTargetPath` 对不认识的工具只能返回 `undefined` → `next()` → 放行（[:58-59](TRIGGER-DESIGN.md#L58-L59)）。§5.1 的用例同样只列这三种（[:211](TRIGGER-DESIGN.md#L211)）。H1 触发于**任意**工具调用；除这三种之外还有哪些工具会写文件（删除 / 移动 / 建目录 / 补丁类 / 第三方插件自带的文件工具），事实包没给，设计也没写「未知工具怎么办」。

**影响**：这是比 §4.3 承认的 bash 绕过更便宜的绕过——不需要构造管道，换一个没被枚举的工具就行，而且它属于「忘了枚举」而非「已知取舍」。更糟的是验证计划与设计假设同源（同样只列三种），所以第四步会全绿。修法不难：把「写」从工具名改为**路径出现即视为可疑**，或对未知工具保守 `deny`/`ask`；bash 也不必假装解析 shell，命令文本里出现 root 段就按可疑处理，比「能识别 mv 但识别不了复杂管道」诚实。

### I6 listener 的 scope 未指定：注册在 agent scope 下，子代理的写调用完全不被拦截

**依据**：事实包明确「scope 过滤：agent-scoped listener 只收该 agent 的调用」（[INTERFACE-FACTS.md:11](INTERFACE-FACTS.md#L11)）。设计全文没有写这条监听器注册在 host 还是某个 agent 的 scope 下（[:57-66](TRIGGER-DESIGN.md#L57-L66) 只有 `ctx.on(...)`）。

**影响**：DSH 里委派是常态。若注册成 agent-scoped，子代理写 `stages/p3/` 一次都不会被看到，且**没有任何报错**——G2 在主代理上「有效」，在整个会话上无效。这是一行代码的决定，但它是「静默失效」类，第四步的用例（[:218](TRIGGER-DESIGN.md#L218) 单会话手写）也不会暴露。

### I7 §4.0 的「局部」采用级别在给出的 config schema 下不可实现

**依据**：schema 只有单值 `enforce: true`（[:165](TRIGGER-DESIGN.md#L165)），但「局部」级的定义是「只对新建项目启用，**老项目配置里 `enforce: false`**」（[:173](TRIGGER-DESIGN.md#L173)）——这要求按项目作用域，schema 没有这个维度。另外 `layout: 'p{n}'`（[:163](TRIGGER-DESIGN.md#L163)）表达不了它自己举的例子 `'00-需求/01-计划'`（有序、非模板）。

**影响**：§4.0 是为了回应 [REVIEW-01-trigger.md](REVIEW-01-trigger.md) 判为第一位的失败原因而加的，但落到 schema 上只剩「全局开」和「全局关」。老项目要旁路，只能把整个机制关掉——恰好是它想避免的「要么全开要么全不开」。这条补丁现在不成立，等于 REVIEW-01 的第一风险仍未处置。

### I8 门的生命周期只覆盖「写之前」：返工不使门失效；`fail` 之后怎么恢复也没写进理由

**依据**：规则只查前置门文件（[:30](TRIGGER-DESIGN.md#L30)）。写 `stages/p1/` 下的产物只查 P0，因此「已过 P1 之后重做 P1 产物」不需要重开门，旧 `pass` 继续生效；`GATE.json` 里也没有时间戳（字段集未定义，见 I4）。另一侧：`fail` 会让所有下游写入被 deny（[:143](TRIGGER-DESIGN.md#L143)），恢复动作只能是把上游门改成 pass，但 deny 理由只有「P1 未通过」（[:143](TRIGGER-DESIGN.md#L143)），**没说怎么解除**。第一轮审计 3.4 节专门提过「误拦的恢复与例外通道；`deny` 的 reason 必须包含怎么解除」（[TRIGGER-AUDIT.md:197](TRIGGER-AUDIT.md#L197)），设计没有回应。

**影响**：实际开发里「返工」比「首次过门」更常见，而门是一次性开关：门证明的是「曾经有人判过」，不是「当前产物被判过」。这就是「简单逻辑在真实场景卡住」的具体形态——不是情形少，是**时间维度缺失**。恢复文案缺失则把误判成本转嫁给不知道规则的人。

## 次要缺陷

**M1 未定义 `verdict` 的默认分支。** `checkGate` 的六种情形里，第 4 条只覆盖「无法解析 JSON」（[:146](TRIGGER-DESIGN.md#L146)）。一个**能解析**但 `verdict` 缺失、为 `null`、写成 `"PASS"`（大小写）、或是空对象 `{}` 的文件，落不进任何分支——实现者只能随手选放行或拒绝。另外 `verdict: fail` 与「缺门」的处置完全相同（都是 deny），六种情形实际只有「可过 / 不可过」两态，状态机（[:129-133](TRIGGER-DESIGN.md#L129-L133)）里的 `进行中`/`未开始` 没有表示，§3.1 是装饰性的。

**M2 §3.2 自称「纯函数」，但第 3 步读盘；§1.2 的样例又与此矛盾。** 标题写「纯函数，可单测」（[:135](TRIGGER-DESIGN.md#L135)），步骤 3 是「读 `stages/p<n-1>/GATE.json`」（[:141](TRIGGER-DESIGN.md#L141)）；样例里 `checkGate(path)` 是同步调用，且**没有观察 `exec.signal`**（[:57-66](TRIGGER-DESIGN.md#L57-L66)），与同节第 71 行「异步门必须观察 `exec.signal`」直接冲突。修法很轻：把签名定成 `checkGate(targetPath, gateRecord)`（纯），I/O 留在监听器里；但这必须在设计里定，否则 §5.1 的「单测对象」是什么都不确定。

**M3 路径语义未定义，而这是全部复杂度的所在。** 规则只说「在 `stages/p<n>/` 下」（[:139](TRIGGER-DESIGN.md#L139)），没有规定：相对/绝对、`\` 与 `/`、Windows 大小写、`..`、符号链接、目标就是目录本身（`stages/p1`）、以及 `mkdir` 类调用。§1.2 还把 `exec.arguments` 说成「解析后的路径」（[:48](TRIGGER-DESIGN.md#L48)），事实包没这么说（[INTERFACE-FACTS.md:11](INTERFACE-FACTS.md#L11) 只列字段，另在 F2 提到 `fs.resolve`，说明路径可能要自己解析）。§1.1 说「规则简单到能写成一句话，不容易出 bug」——这句话是反的：判定简单，**路径归一化不简单**，bug 全在那儿。顺带：§1.3 担心的「写台账要绕过 G2（自指）」（[:97](TRIGGER-DESIGN.md#L97)）并不存在——`stages/_ledger.jsonl` 不在 `stages/p<n>/` 下，按规则 1 本来就放行。

**M4 台账记录没有项目标识。** 记录只有 `stage`/`at`（[:80-90](TRIGGER-DESIGN.md#L80-L90)），H15 是 profile 级、跨会话的 KV（[INTERFACE-FACTS.md:26](INTERFACE-FACTS.md#L26)）。同一 profile 下两个项目各有一个 p1 门，台账里无法区分；而 [TRIGGER-PLAN.md:101](TRIGGER-PLAN.md#L101) 要求「按阶段查、按时间查」，多项目时会串。镜像 `stages/_ledger.jsonl` 是每项目一份、KV 是全局，两者冲突时谁是权威也没定。

**M5 `ask` 态从头到尾没被讨论。** H1 有四态（[INTERFACE-FACTS.md:11](INTERFACE-FACTS.md#L11)），第一轮审计把 `ask` 列为「手动放行」的候选并要求确认留痕（[TRIGGER-AUDIT.md:227](TRIGGER-AUDIT.md#L227)）。设计只用 `deny`。不采用 `ask` 可以（它给不了台账），但要写一句为什么不，否则下一个读者会以为漏看了。

**M6 范围收缩没同步到计划第四步的验收判据。** [TRIGGER-PLAN.md:194](TRIGGER-PLAN.md#L194) 仍要求「G1/G2/G3 **各**至少一条 L1 证据」，而 G1 已缓做。设计没有指出这条要改，第四步验收时会撞上一个不可满足的字面判据。

**M7 shadow 模式的记录类型未定义，`layout` 例子与模板不符。** §1.3 的 schema 是「门记录」，§4.0 要记「本可以拦住 N 次」（[:176](TRIGGER-DESIGN.md#L176)），这是**拦截记录**，两种记录混在一张表里没区分；`enforce: false` 时到底由哪个接缝记这条，也没写。

**M8 卸载重装后老门「复活」，没有新鲜度检查。** §4.1 说卸载后 `GATE.json` 留着当历史（[:184](TRIGGER-DESIGN.md#L184)），重装后它们立刻重新生效。半年前写的 `pass` 会直接给今天的产物开门，且无提示。低危，但和 I8 的时间维度是同一个洞。
