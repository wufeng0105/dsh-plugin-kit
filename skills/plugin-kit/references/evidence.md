# 可信度与边界

> 这一篇主张：**这套东西不是设计出来的，是三轮真实开发跑出来的——包括它在哪里不成立。**
>
> 读完这一篇你该能判断：什么时候该信它，什么时候不该。

**为什么这两件事写在一篇里**：可信度和边界是同一个问题的两面。只说「我们证明了什么」而不说「哪里没证明」，会让人以为已经安全——**不知道边界的规格比没有规格更危险**。所以「证据」和「还没关掉的边界」必须放在一起读，分开会漂移。

---

## 一、它是怎么被验出来的

### 实验设计

拿三个真实插件的**需求**当靶子（不是代码），按正常开发流程各跑一遍，逐阶段记录卡点。阶段序列固定：需求 → 计划 → 探针 → 执行 → 验证 → 修复 → 交付 → 维护。

三条设计原则：

**一、需求是「干净」的。** 派给开发者的只有需求文档，没有「要按什么流程做」的提示。否则它会照着答案演，卡点被提前消掉，机制也就推不出来。

**二、每个阶段换一个人。** 阶段之间靠磁盘产物交接，模拟真实项目里的换人接手。这样「上一个人没写清楚」的代价会立刻显现。

**三、规格逐轮演进。** 第一轮没有规格；第二轮带着第一轮归纳的规格；第三轮带着修补后的规格。规格本身也是被检验的对象。

### 三轮结果

| 轮次 | 需求 | 走到哪 | 测试 | 结论 |
|---|---|---|---|---|
| 一 | enhance | P0–P5 全跑完 | 153/153 | 流程能端到端跑通 |
| 二 | draft-studio | P0–P3b | 178/178，变异 14/14 | 带条件可进 P4 |
| 三 | teammate-picker | P0–P3b | 111/111，tarball 真加载 | 2 个 BLOCKER 修复闭环 |

三轮都在「不许安装到真实环境」的约束下跑，所以**运行时验证普遍缺失**——所有需要真实安装才能验的项，结论都是「无法判定」。这是环境限制，不是遗漏。

### 规格本身的演进

规格改了三版，每版都是被上一版的事故逼出来的：

| 版本 | 被什么逼出来 |
|---|---|
| 一 | 无规格，第一轮直接跑 |
| 二 | 第一轮暴露：自评全绿不等于验收过、空真、错误前提跨阶段传播 |
| 三 | 第二轮暴露：规格自身时序矛盾（允许未验项进执行阶段，执行阶段入口又要求清零） |
| 四 | 第二轮暴露：模块有测试有但产品没接线、验收分类用「需运行时验」兜底、计数手算错、防漂移测试自带常量 |

### 审查员抓到了什么（这是最硬的部分）

**每一次打回，写的人都自评过「没问题」。**

| 轮次 | 抓到什么 | 写的人当时的自评 |
|---|---|---|
| 一 | 身份段名写错；检查函数假成功；配置字段类型不符 | 138 个测试全绿 |
| 一·复审 | 修复引入两个新陷阱；「永远不成功」隐患 | 153 个测试全绿，七处修复有红绿证明 |
| 二 | 把列表座位说成「容差妥协」；19 条缺陷 | 21 条验收、18 条依赖 |
| 二·复查 | 返工欠新账两条（观测字段不存在）；措辞级矛盾七条 | 清账 19/19 |
| 二·验证 | **产品没接线**；验收分布造假；防漂移测试造假（3 BLOCKER / 6 MAJOR / 7 MINOR） | 138 个测试全绿，声称分布诚实 |
| 二·复验 | 四条必修，其中一条方向反了；两个缺陷仍复现 | 174 个测试全绿 |
| 三 | 客户答复未吸收；「无需自建存储」自相矛盾；降级违反客户裁定 | 16 条验收全机判 |
| 三·验证 | 恢复功能运行时不可达（用官方状态重放证伪）；配置恒为空 | 81 个测试全绿 |
| 三·修复 | 配置问题实为两个缺陷叠加 | 声明已修 |

**九次打回，九次都是「写的人自评通过、审查员判不通过」。**

### 每条铁律的出处

| 漏洞 | 现在的铁律 |
|---|---|
| 自评全绿不等于验收过；没接线也能绿 | 空真排除 |
| 修复把假阳性换成假阴性 | P3b 复审三问 |
| 错误前提跨阶段传播 | 二手结论不得当前提 |
| 环境暂时不可用被固化成永久结论 | 环境状态不得固化 |
| 规格自身时序矛盾 | P1.5 探针门 |
| 「可机判」的观测字段不存在，负例永不红 | claim-vs-evidence 对账 |
| 取证工具本身坏了（矩形序列化成空对象） | 证据工具自检 |
| 客户答复未回填，文档还写「待裁定」 | 内部一致性 |
| 宿主限制被写成「验收退化」 | 宿主限制声明三件套 |
| 模块有、测试有、产品没接线 | 接线可达性 |
| 验收分类用「需运行时验」兜底 | 验收分类禁兜底 |
| 验收计数手算错误 | 计数机检 |
| 防漂移测试自带常量 | 防漂移测试不得自带常量 |
| 打包漏文件，测试全绿但装不上 | 打包后必须真加载 |
| 交付命令从未被跑过 | 交付命令必须真跑 |
| 缺陷清单会过期 | 缺陷清单会过期 |
| 负责人复核只读代码不执行 | 复核必须执行 |
| 显示形态 ≠ 契约形态 | 显示形态 ≠ 契约形态 |

## 二、还没关掉的两条（用这套东西之前先读它）

**它们不是待办清单，是「这套东西可能不成立」的地方。** 每条都写了「怎么才算关掉」——没有可判据的，不列在这里。

### 一、成本：测过一次，但只回答了一半（部分关闭）

这套机制要求你改变工作方式：项目里建 `stages/` 目录、每阶段写一个 `GATE.json`、根目录放一个 marker。**它省下了「反复强调」的成本，但增加了别处的成本。**

**2026-11-10：第一次真实项目实测（E 阶段）**

在 `dsh-archive-manager`（界面型插件，设置页批量管理归档会话）上走完 P0–P5，记满三列：

| 列 | 值 |
|---|---|
| 总额外耗时 | **204 分钟**（P5 快照 160 + 用户负向证据后的修复 12） |
| 开门次数 | **6 次**（每次 2 分钟，共 12 分钟） |
| 维护 stages 目录 | **9 分钟** |
| 事前止损线 | 288 分钟（工期 960 分钟的 30%） |
| 占比 | **70.8%** |

**构成**：返工类 71 分钟（41.8%）、P0–P1.5 41 分钟、P2 实现 25 分钟、P3.5 真机 14 分钟、用户负向证据修复 12 分钟。

**收益侧**：流程拦下 **12 起**会流到用户面前的问题（销毁语义写进确认框、幽灵引用、网关名排实施期、GOAL 自身过期、状态绑定错位三连环、inject 未声明、自造槽名、L1 等级标宽、`slots.register` 被塞进 `inject` 回调导致设置页不渲染）。

**第 9–12 起都来自用户，不是审查员**。这四起是本次实验最重要的发现：

| # | 用户看到的现象 | 真正的根因 | 为什么内部没抓到 |
|---|---|---|---|
| 9 | 设置页没有条目 | 插件只在 P3.5 的一次性 profile 里，日常 profile 从未装过 | 拆 profile 是流程要求的动作，但没人复核「装到哪去了」 |
| 10 | 补装后仍空白 | `slots.register` 被塞进 `slots.inject` 回调（inject 是门控不是注册入口） | 离线 DOM 桩测的是逻辑，不是宿主注册契约 |
| 11 | DSH 起不来 | `client.js` 用 ESM `export`，宿主把所有 client.js 拼成大脚本 → `SyntaxError` | 单文件 `node --check` 是合法 ESM；无一条测试验「宿主怎么加载」 |
| 12 | 修复后仍起不来 | ① 只装最小 profile 测不出完整插件集冲突 ② `Config = {}` 不是 schemastery Schema | ① 验证环境与真实环境 bundle 数不同 ② 同样属于「宿主加载契约」盲区 |

**新增的三条护栏**：C4（注册必须在 inject 之外）、C5（模拟宿主拼接脚本 parse）、C6（Config 必须是 Schema）。

**现有状态**：插件在**最小配置下启动干净**（零 warning、零崩溃日志、L1）；但**完整插件集下曾崩溃，至今未拿到堆栈**，界面是否真的渲染**仍未验证**。项目已停止，结论见 `dsh-archive-manager/stages/COST-VERDICT.md`。

**为什么只算「部分关闭」**：字面判定是 204 < 288 → 机制成立。**但不接受这个字面结论**，三个理由：

1. **工期 960 分钟是凭空估的**，按「熟练后」估，而 E 阶段是第一次走完整流程，含大量学习成本。分母被人为抬高。
2. **项目没交付完**：UI 未做 L1 验证、插件没真正发布。分子分母都会变。**而且第 12 起缺陷正是「UI 未验」流到用户面前的实证。**
3. **返工占 41.8%**，是流程的固定开销而非一次性学习成本。下一个项目会不会少——**不知道**，因为只有一个样本。

**现在的状态**：

> **L1 从「成本从未测过」变为「测过一次：204 分钟 / 6 次开门 / 9 分钟目录维护，占事前止损线 70.8%」。**
> **这个数支持「流程能抓到真问题」，不支持「流程划算」。** 标「部分关闭」，不标「关闭」。
> **且第 12 起说明：流程内部没抓全，最后一道防线是用户。**

**怎么才算真正关掉**：换一个作者、换一类插件形态再跑一次，记同样的三列；**并且事前把工期估计的口径写死**（不许事后改分母）。两个样本都低于止损线，才谈得上「机制成立」。

### 二、「换人」从没真的换过（最根本的一条）

`protocol.md` 规则 4 给「结构性」下的定义是：

> 换人、换插件仍会再遇到。

**这一半从来没测过。**

三轮实验的三个阶段确实各开了全新上下文——但都是**同一模型、同一作者、同一台机器、同一 DSH 版本**。所以：

| 这句成立 | 这句不成立 |
|---|---|
| 审查员**没参与写** | 审查员**是另一个人** |

**为什么这是最根本的一条**：机制之所以有效，是因为「没参与写」——**这一点验证了**。但「结构性」这个归纳前提，需要的是「换人也一样」——**这一点没验证**。

**后果**：如果换一个作者、换一个模型后，门打回的地方完全不同，那这套判据就不是「结构性的」，只是「这个人踩过的坑的清单」。

**怎么才算关掉**：**换一个执行者重跑同一批需求**（至少换一项：作者 / 模型 / 机器 / DSH 版本）：

1. 用 `requirements/` 里同一份需求
2. 记录**门打回的位置**
3. 与第一轮对比：重合率是多少

**事前写死重合率下限**（例如「至少 50% 的卡点重合」）。达到 → 「结构性」成立；达不到 → **整个归纳前提被证伪**，这套东西只对特定作者有效。

**现在的状态**：**没测。** 而且 `EVIDENCE.md` 的验收条件里有一条（「两个人看同一份台账会得出同一结论」）**依赖一个不存在的第二个人**。

## 三、另外七条边界（不必单独记，但结论依赖它们时要降级）

### 三、运行时验证：机制已实测可用，但真项目上还没跑过

三轮都受「不许安装」约束。结果是：**没有一条验收是在真实安装环境下验过的**——这套规格能保证「代码路径通」，不能保证「功能真的可用」。（以上说的是 **2026-11 之前**的情况。）

后来补了 P3.5（一次性 profile 的运行时验收）。机制本身已实测可用：建 profile → 装 → 验 → 拆，全程不碰日常 profile。**它已经在多个真实插件上跑过**（`dsh-enhance`、`draft-studio`、`teammate-model-picker`，以及本 skill 自己的插件形态 `dsh-plugin-kit`），抓到过「离线全绿、真机失效」这一类缺陷。

**还空着的一格**：在一个**真要交付的项目**上从头走完 P0–P5。机制能用，不等于它在交付压力下够用。

### 四、中间态不可复跑

支撑 23 条铁律的那些事故，大部分证据是报告里的文字，不是可复跑的快照：

- 第一轮的验证探针脚本跑完就删了；
- 第二轮、第三轮的探针大多在系统临时目录，没有入库；
- 修复前的「红」状态没有逐轮存档。

**能复跑的是终态测试**（153/178/111 都还能跑），**不能复跑的是「当时确实是红的」这个断言**。这条边界必须写出来：你看到的 23 条铁律，每条的出处是报告，不是可重放的实验。

**部分关掉**：`dsh-plugin-kit` 有 `test/e2e/run.mjs` + `evidence/` 存证。

### 五、第三轮的「111/111」掩盖了五项未通过

第三轮修复后测试全绿、tarball 真加载，但客户端面仍有五项验收无法通过（模型目录、会话事件、设置写入、显示开关、恢复操作）。修复报告里明确写了「只做到不再谎称已就位，没实现功能」。

**测试数不是验收数。** 这一条本身就是铁律的实例：111 个测试通过，不等于 16 条验收通过。

### 六、第二轮的终验是「带条件可进 P4」，不是「通过」

终验给了九条条件，包括：补证据命令生成器、写清无法界面验证的负例、首帧竞态必验、客户明确同意降级。这些条件没有全部执行完。

### 七、台账里有一处我自己写反了

台账第 59 条原文写「两个缺陷在 P2 后期已被自然修好」，这与复验报告的「仍然复现」矛盾，也与铁律 22 记录的「负责人误判」矛盾。

**正确的事实是**：那两个缺陷在修复轮开工前**并没有修好**；负责人读代码判定「已修好」是错的；修复轮实跑探针复现后，才把它们真正修掉。台账那一条的措辞已订正。

这一条留在这里而不是悄悄改掉，因为它是这套机制最想说明的事：**连写规格的人自己都会在台账里写下自相矛盾的记录**——所以才需要另一个不参与写的人来读。事实上，这一处正是独立审计发现的。

### 八、样本只有三个，而且形态不够分散（E 阶段补了第四个，仍不够）

三个需求分别偏向：配置型、界面型、宿主集成型。但三者都出自同一个作者、同一台机器、同一套宿主版本。**换一个作者、换一个宿主版本，判据可能需要调整。**

**2026-11-10 补**：E 阶段在真实交付压力下跑了第四个项目 `dsh-archive-manager`（界面型，设置页批量管理归档会话）。它带来一条此前没有的证据：**界面型插件的 P3.5 无法用 CLI 驱动验证**，UI 交互项只能标 `UNVERIFIABLE`（详见 `process.md` P3.5 卡的形态例外）。

但四个样本**仍是同一作者、同一模型、同一台机器、同一宿主版本**。形态分散度改善了一点，「换人仍会遇到」这一半**仍然没测过**——它和第二节是同一个缺口。

### 九、审查员会误判

它漏过（第三轮修复后的五项未通过，直到终验才写清），也错过（第二轮把「需要更多证据」判成「不可进」，导致多返工一轮）。它不是一个可靠的裁判，它是一个**比自评更可靠的裁判**。

### 十、这套东西有维护成本

- **每道门要人工触发。** 它不是 CI，不会自动跑（插件形态可用 `tools/pre-execute` 机械拦截，但 marker 仍要人建）。
- **判据要靠事故喂养。** 23 条铁律里没有一条是凭空想出来的，全是踩过之后补的。你遇到新的事故，就该往里加。
- **审查员会自己发明标准。** 规格写得含糊时，它会按自己的理解判——所以出口判据必须写成「能判真假」的句子。

## 五、这份文件自己怎么用

**每次有结论性动作前读一遍**，问两句：

1. 这次的结论依赖成本假设吗？——如果依赖，而成本只测过一半，结论要降级
2. 这次的结论依赖「换人仍然成立」吗？——如果依赖，而独立性没测，结论要降级

**这两问的答案会改变很多结论的强度。**

比如「九次打回证明了机制有效」——它证明的是「**这个作者的**机制有效」。

---

## 结论

**成立的部分**：把检查从写的人手里拿走，确实能抓住自评抓不到的错。九次打回，九次都是这个结构。

**不成立的部分**：判据要靠事故喂养，审查员会误判，中间态它留不住，真项目交付这一格还空着，「换人」这一半从没测过。

**知道这两半，才算真的会用它。**
