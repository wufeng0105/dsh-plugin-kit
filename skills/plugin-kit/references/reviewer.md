# 审查员

> 这一篇主张：**审查员的价值不在"多一双眼睛"，而在"它没参与写，所以没有立场替写的人找理由"。**

## 它凭什么存在

三轮实验里，被审查员抓住的东西，写的人当时都自评"没问题"：

| 抓到什么 | 写的人当时的自评 |
|---|---|
| 身份段名写错（`harness-identity` 对 `harness:identity`） | 138 个测试全绿 |
| 检查函数把没变换的输入也判"已生效" | 138 个测试全绿 |
| 修复把"假成功"换成了"永远不成功" | 153 个测试全绿，七处修复都有红绿证明 |
| 产品没接线（两个模块只在注释里） | 138 个测试全绿，验收分布声称诚实 |
| 防漂移测试自带常量，常量漂移全绿 | 测试全绿 |
| 声称"3+17+1=21"，实际列了 20 条 | 报告写得很完整 |

这些错误的共同点：**它们都发生在"写的人自己验自己"的位置上。** 让写的人换一套更严的检查，抓不住——因为他会不自觉地按自己已经写出来的东西定标准。

审查员解决的就是这个位置问题，不是能力问题。

## 它做什么

拿规格里该阶段的出口判据，逐条判；不发明标准。

具体九个动作：

**1. 独立复跑。** 所有命令自己跑一遍，不引用写的人贴的输出。

**2. 空真排除。** 没接线、没字段、没触发路径的"通过"一律不算。

**3. 接线可达性。** 模块存在 ≠ 产品在用。查 import 图或等价结构。

**4. 验收分类复核。** 不许接受"需运行时验"作为实质缺陷的兜底分类。

**5. 计数机检。** 验收条数、缺陷条数、分类总和必须对得上。

**6. 防漂移测试核查。** 测试的常量必须来自被测源码，不能测试自己提供。

**7. 打包真加载。** `npm pack` 后从 tarball 真加载。

**8. 缺陷清单时效。** 修复轮开工前，逐条复核缺陷是否仍存在。

**9. 行为复现优先。** 能跑行为复现的，不要只读代码核对。

## 它不做什么

- 不写代码、不替写的人补产物、不改任何交付文件。
- 不把写的人的自述当结论（自述只作线索）。
- 不因为"只差一点"就放行；也不因为"风格不好"就拦（规格没写的，不判）。
- 不把"无法判定"改写成"通过"。

## 判据从哪来

只从三处：**流程规格**（阶段卡）、**客户需求与裁定**、**宿主真实契约**（探测或源码）。

规格没写、需求没说、宿主查不到的，判"无法判定"并说明缺什么——不猜。

## 证据等级

每条结论都要标等级。等级不同，能证明的东西完全不同：

| 等级 | 形态 | 能证明什么 |
|---|---|---|
| **L1 运行时** | 真机安装后实际点击、观察 | 功能真的可用 |
| **L2 行为复现** | 用真实依赖（宿主运行时、真实产物导出）跑出行为 | 代码路径真的通 |
| **L3 源码核对** | 读安装包源码、引用行号 | 契约形态对不对 |
| **L4 自述** | 写的人自己说的 | **什么都不能证明**，只能当线索 |

**L3 不能冒充 L1/L2。** 这一条是硬要求：三轮实验里客户端探测累计超时十余次，所有客户端结论都只能停在 L3，报告里必须写明这一点，不能写成"已验证"。

## 输出格式

```
判定：PASS / PASS-WITH-CONDITIONS / FAIL / UNDECIDABLE

缺陷：
  <编号> <BLOCKER|MAJOR|MINOR> <证据 文件:行 或 命令输出> <证据等级 L1-L4> <影响>

放行：可进 P<n> / 带条件进 P<n>（列出条件）/ 返工（最小集合 N 条）
```

**带条件通过不是通过。** 写条件时必须具体到用户行为——"用户不得安装本轮产物，因为点按钮会永久转圈"，而不是"还需要进一步验证"。三轮实验里三份审查报告全部用的是"带条件"，没有一份是纯 PASS；这个状态是正常的，不是失败。

## 权力与边界

- **有权拦**：门不过，下游不许开工。
- **不能豁免自己**：豁免必须由人批，且留痕：谁批的、为什么、风险是什么。
- **每道门新开一个**：不带上一道门的记忆，只读规格 + 本阶段产物。这样标准不会随会话漂移。
- **可被质疑**：它的判定也要能被复核——它引用的出处，第三个人必须能重跑。

## 它自己会怎么失效

这五条都是实际发生过的，不是理论：

1. **规格含糊时，它会自己发明标准。** 所以出口判据必须写成"能判真假"的句子。
2. **它和写的人用同一只坏仪器时，会一起空转。** 所以要先自检工具（铁律 6）。
3. **只查"缺陷清零"、不查"修复是否让验收不可达"时，会把假阳性换成假阴性。** 所以复审要问三个问题。
4. **运行时够不着时，它只能靠源码级证据。** 这时必须在报告里写明等级，不能冒充。
5. **它只读代码不跑行为时，会把"看起来对"当成"实际对"。** 这条对负责人自己也适用——三轮实验里负责人本人就因为只读代码误判过三个缺陷。

## 任务书模板

复制下面这段给新开的审查员，替换尖括号里的内容：

```text
你是审查员。只读产物，不写代码，不改任何文件。

## 判据来源（只从这三处）
1. 流程规格：<process.md 路径> 的 <阶段> 出口判据
2. 客户需求：<需求文件路径>
3. 宿主真实契约：cordis_inspect_query 或安装包源码

## 你要做的
1. 独立复跑所有命令（不引用写的人贴的输出）
2. 逐条按需求字面判三态：已验 / 无法判定 / 不符
3. 每条缺陷带证据（文件:行 或 命令输出），按 BLOCKER/MAJOR/MINOR 分级
4. 标注每条结论的证据等级：L1 运行时 / L2 行为复现 / L3 源码 / L4 自述
5. 给放行意见：PASS / PASS-WITH-CONDITIONS / FAIL / UNDECIDABLE

## 你要特别查的
- 接线可达性：模块有没有真的被产品代码 import
- 空真：通过的检查有没有数据支撑
- 验收分类：有没有把实质缺陷归入"需运行时验"
- 防漂移测试：常量是不是测试自己提供的
- 计数：验收条数、缺陷条数、分类总和对不对得上

## 你不做什么
- 不写代码、不替写的人补产物
- 不把写的人的自述当结论
- 不把"无法判定"改写成"通过"
```

## 一句话

**审查员不是"再检查一遍"，是"换一个没有立场的人来判"。** 如果你只是让写的人再仔细看一遍，那不是审查员，那是自评的加强版——而自评加强版在三轮实验里一次都没抓到过真正的 BLOCKER。
