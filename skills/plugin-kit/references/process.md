# DSH 插件开发流程规格

> 这一篇主张：**把"检查"从写的人手里拿走，交给一个不参与写的审查员，能抓住自评永远抓不到的错。**
>
> 反面是"只要规范写得够清楚、让 AI 照着做就够了"。材料否证了它——带规格的两轮开发仍各自被门打回四次和两次，其中一轮的规格自身还有时序矛盾。
>
> 代价要写在前面：这套东西**不会自动运行**，每道门要人工开；判据也不是凭空来的，是三轮事故喂出来的。

## 给谁用

**给已经会写 DSH 插件的人。** 它是一份阶段门与审查清单，不是从零教学。

如果你还没装成功过一个最小插件，先去做那件事：让一个能显示文字的插件真的装上、点一下、看到效果。装不上的时候，这份规格里每一条你都会看不懂——因为它们讲的都是"做对了之后怎么防止做歪"。

如果你已经写过插件，并且遇到过下面三种情况中的任意一种，这份东西对你有用：

- 测试全绿，装上却发现按钮点了没反应；
- 需求明明写清楚了，做到一半做法已经跟需求不一样；
- 每次新会话都要把同一批要求再说一遍。

## 为什么需要它

三轮实验里，问题不是"写得不好"，是**坏在看不见的地方**：

| 失败模式 | 具体形态 | 自评能不能发现 |
|---|---|---|
| **没接线** | 模块写了、测试全绿，但产品代码没 import 它，按钮点了立刻回到空闲 | 不能。测试只测模块，不测接线 |
| **空真** | "全部开关关闭时与宿主一致"——当时压根没接线，所以当然一致 | 不能。它确实"通过"了，只是通过的原因不对 |
| **假绿** | 负例检查用的观测字段不存在，那条负例永远不会红 | 不能。绿就是绿，看不出为什么绿 |

这三种的共同点：**它们不在任何一段代码里，而在"段与段之间"。** 逐段检查一律看不见。

所以这套东西的重点不是"把每段写好"，是**保住阶段之间的状态**——上一阶段承诺的事，下一阶段有没有接住。

## 机制：阶段门与审查员

一句话：**每个阶段结束时，开一个独立的、只读产物的审查员；它按文件化的出口判据判三态，不通过则下游停摆。**

两个角色分工明确：

- **写的人**：从需求做到交付，产出所有东西。
- **审查员**：不写代码、不改产物、只读、只出结论。

**为什么必须是新开的一个。** 写代码的那个 AI 有立场——它会替自己的实现找理由，会把"我觉得没问题"说成"已经验过"。新开的审查员没有这个包袱，它不知道上一轮发生了什么，只能看产物。这是整套机制唯一不可替代的地方：**一致性来自文件，不来自任何 AI 的记性。**

审查员具体怎么判、判完怎么表达，见 `reviewer.md`。这一篇只讲每个阶段该产出什么。

## 23 条铁律

铁律是跨阶段通用的硬规则。每条后面括注的是它换来的那次事故——**没有事故的规则不该进这张表**。

### 证据类

**1. 可复跑。** 任何"已验"必须能被第二个人用你留下的命令原样跑出来。

**2. 空真排除。** 没接线、没数据、没触发路径的"通过"不算通过。（事故：验收"全关时与宿主一致"，当时根本没接线。）

**3. 三态。** 已验 / 未验 / 无法判定。不许把"无法判定"写成"通过"。

**4. 二手结论不得当前提。** 别人报告里的断言，引用前先复核。

**5. 断言必须有出处。** 关于宿主能力的断言（"只有/没有/必须/不支持"），附探测命令+返回，或安装包 `文件:行`。审查员复核出处，不复核措辞。

**6. 证据工具自检。** 判据用的观测手段，先证明它能取到非空值，再用它判红绿。（事故：`DOMRect` 序列化成 `{}`，所有矩形判据空转。）

**7. claim-vs-evidence 对账。** 每个断言去找它的证据；找不到就降级为"未验"。

**8. 证据口径。** 只认「文件:行」或「命令+输出」。截图、日志、口头说明只能作补充。

**9. 环境暂时状态不得固化。** 探测失败要记录当时的环境前提（宿主是否重启、页面是否在线、端口是否变化），并保留重探义务。

### 诚实类

**10. 状态诚实。** 不把"我记录了"写成"客户批准了"；不把"没验"写成"预期如此"。

**11. 归因也需证据。** 失败归因本身要有证据。（事故：配置读不到归因"缺依赖"，实为类型判断写错；探测超时归因"页面没开"，实际页面在线。）

**12. 客户裁定需证据。** 裁定不是"我说了算"，是"在证据基础上选择"。裁定不可达时必须明确写"作废并重裁"。（事故：负责人裁定某条语义，被审查员用官方状态重放证伪。）

### 结构类

**13. 接线可达性。** 模块存在 ≠ 产品在用。凡"已实现"的模块，必须证明它在产品 import 图里可达。（事故：两个模块只出现在注释里，138 个测试全绿，按钮点了没反应。）

**14. 验收分类禁用兜底。** 不许把实质缺陷归入"需运行时验"。分类只有：已离线证 / 确实需安装（说明缺什么）/ 缺陷。

**15. 计数机检。** 验收条数、缺陷条数、分类总和必须机检，不许手算。（事故：声称 3+17+1=21，实际列了 20 条。）

**16. 防漂移测试不得自带常量。** 防漂移测试必须从被测源码抽取全部常量，测试自己提供常量等于没测。（事故：三处常量漂移，测试全部保持绿色。）

**17. 打包后必须真加载。** `npm pack` 后从 tarball 真加载一次。（事故：`files` 漏一个被硬 import 的文件，单测全绿但 tarball 起不来。）

**18. 交付命令必须真跑。** 写进交付说明的命令，必须自己跑一遍。（事故：`npm test` 写错路径，从未被跑过。）

### 流程类

**19. 环境占用盘点。** 开工前盘点目标环境已有占用物（同座位、同包名、同功能是否已在跑），任务书写明并存策略。

**20. 宿主限制声明三件套。** 源码出处 + 客户知情记录 + 对验收的影响写法。缺一件不算声明，算退化。

**21. 缺陷清单会过期。** 修复轮开工前必须先复核缺陷是否仍然存在。

**22. 复核必须执行，不能只读。** 判"某个缺陷是否已修"必须实跑复现用例，不许看代码像对的就下结论。**这条对负责人自己同样适用。**（事故：负责人读了一段合并逻辑就判定两个缺陷"已修好"，实跑后发现两个都还在。）

**23. 显示形态 ≠ 契约形态。** 同一份目录记录里可能同时给"显示 id"和"契约 id"，两个字段并存时要确认哪个是契约值。（事故：目录显示 `include:<patchId>`，真正的设置命名空间是裸 `patchId`。）

> **铁律 23 是例外，其余 22 条是流程判据。** 第 23 条其实是**领域契约知识**（宿主的一条事实），本该归内置 skill——但内置**没有记载**这处 id 二元性（实测：内置 33 个文件全文无 `patchId` / `include:` / `options.id`），所以只能留在这里。读的时候区分一下：前 22 条说"流程要怎么做"，第 23 条说"DSH 有这么个坑"。**后者会随宿主升级变化，前者不会。**
>
> **版本基线**：这条事实核对自 DSH 0.2.2-rc.1。宿主升级后要重验——重验方法：对一个已装插件同时看 `Config.listConfigs` 返回的 `id` 与 `patchId` 两个字段是否仍然不一致。

## 阶段卡

六个阶段，外加一个探针门、一个修复子阶段和一个运行时验收阶段，共九张卡。每张卡三栏：**入口**（开始前手上必须有什么）、**产物**（必须留下什么）、**出口**（怎么算过）。

### P0 需求

**入口**：客户材料。

**产物**：需求文档 = 逐条验收标准（操作 → 观察 → 判定）+ 歧义清单 + 不做清单。

**出口**：

- 每条验收能判真假；含"靠人看"的必须给可机判的替代，否则标"人工判读"；
- 歧义清单每条标「客户裁定 / 自查可解」，自查可解的不许上抛；
- 不做清单具体到能反驳"那做个 X 行不行"；
- 验收计数机检（条数 + 分类 + 总和）。

### P1 计划

**入口**：P0 通过。

**产物**：计划（形态判断、开发顺序、每步完成标志）+ 依赖清单 + 风险清单 + 环境占用盘点。

**出口**：

- 依赖清单每条：引用点 / 为什么非它不可 / 探测结论或 `UNVERIFIED` / 不成立时的降级；
- 每步有完成标志；最大风险有应对；
- 内部一致性自检表覆盖全部关键数值与口径。

**技术细节见**：形态判断与扩展点选择在 `cordis-plugin-development`；「该放 Host 还是 preset」在 `editing-cordis-compositions`；可装包清单在 `cordis-composition-reference`。

### P1.5 探针门

**入口**：P1 通过，且存在 `UNVERIFIED`。

**产物**：探针记录（每条 `UNVERIFIED` → 结论 + 出处）。

**规则**：只探测、不写功能代码；需要安装只装探针。

**出口**：每条变成 已验 / 已定降级（写明验收如何变）/ 无法判定 + **由谁在何时接受该风险**。清零后才进 P2。

### P2 执行

**入口**：P1.5 清零，或客户明确豁免。

**产物**：代码 + 自验证据（命令与输出）。

**出口**：

- 语法通过；
- 测试通过，且**至少一条被证明能变红**（改坏 → 红 → 改回 → 绿）；
- **接线可达性检查**通过（import 图或等价结构）；
- 防漂移测试的常量来自被测源码；
- 每条自验命令写进交付说明，别人能复跑；
- **探针脚本入库**（`probes/`），不留在临时目录——跑完就删的探针等于没跑，因为第二个人无法复现；
- **红态输出存档**（`probes/red/`），修复前跑一次并保存原始输出，证明"当时确实是红的"。

**技术细节见**：这个阶段是内置 skill 的主场——插件形态、扩展点选择、Host 半/浏览器半怎么写、UI 规则、MCP 接入、配置持久化，全在 `cordis-plugin-development`；patch 写法在 `cordis-composition-reference`；要动 preset 在 `editing-cordis-compositions`。**这里不重复它们，只说"这一阶段需要哪类知识"。**

### P3 验证（独立审查员）

**入口**：P2 全部产物 + P1 的依赖清单（用于复核断言出处）。

**产物**：验证报告：逐条按需求字面判三态 + 缺陷清单（BLOCKER / MAJOR / MINOR）。

**出口**：

- 每条缺陷带证据，并标注证据等级（见 `reviewer.md`）；
- 空真被排除；
- 验收分类不用"需运行时验"兜底；
- 放行意见明确：通过 / 带条件通过 / 不通过。

### P3b 修复

**入口**：P3 缺陷清单，且**已逐条复核缺陷是否仍然存在**。

**产物**：修复报告（每条：修法 + 红→绿证明 + **修复前的红态快照路径**）。

**出口**：走 P3 同一道门；复审必须回答三个问题——

- 缺陷真的清了吗（不是被换成了别的形态）；
- **验收是否仍然可达**（有没有把假阳性换成假阴性）；
- 有没有新引入的缺陷。

### P3.5 运行时验收

**入口**：P3 或 P3b 放行，且验收清单里存在**只能在运行时验**的项。

**产物**：运行时验收记录（每条：操作 → 观察 → 结论 + 证据等级 L1）。

**做法**：用**一次性 profile**，不碰日常 profile。四个动作固定：

1. **建** — 从 shipped 模板创建一个新 profile，只创建不启动
2. **装** — 把待验的包装进去
3. **验** — 启动该 profile，按插件形态选观察面
4. **拆** — 删掉这个 profile 目录

**这几步的具体命令随宿主版本变化**，且 `plugin-kit` 与内置 skill 都不记载它们（实测：内置 4 个 skill 全文没有 `--from-default-profile` / `plugin --profile` 的任何记载）。正确的做法是：

```powershell
# 先看当前版本怎么调
dsh --help
dsh plugin --help
```

**三条已知的坑**（与版本无关，是语义约束）：

- **`--from-default-profile` 是替换语义**，不是"基于模板新建"——同名已有 profile 会被覆盖；
- **不能与 shipped 模板同名**（如 `web`），否则会撞；
- **顺序有依赖**：必须先建后装。先装会用默认 bundle 集初始化，而不是你想要的那个模板。

**拆 profile 时用变量，不要写死路径**——`$DSH_HOME` 可能被覆盖：

```powershell
Remove-Item -Recurse (Join-Path $env:DSH_HOME "profiles\smoke")
```

**形态例外（2026-11-10 E 阶段实证）**：上面第 3 步「启动该 profile 观察」隐含「观察面可由 CLI 或自动化驱动」。**界面型插件打破这个假设**——它的验收对象就是 GUI 本身，而 web profile 的 CLI 不接受任务参数、GUI 端口需鉴权、当前 GUI 又常驻在另一个 profile 上。

遇到这种情况：

- UI 交互项**标 `UNVERIFIABLE`**，写明「需要独立 GUI 实例或带鉴权页面自动化」，不得冒充通过；
- 装配层（能装、配置树、模块加载）如实标 **L2/L3**，**不标 L1**——L1 只给「装上后实际点击观察」；
- 交付说明必须写明「装上不保证可见可用」；
- 这条缺口要回写到证据边界（样本形态）——已完成：`evidence.md` 第三节（样本不分散）记了「界面型插件的 P3.5 无法用 CLI 驱动验证」。

**不要为了拿到 L1 去启动第二个 GUI 实例干扰用户正在用的界面**——那是用验证成本换验证结论，本末倒置。

**模块形态条款（2026-11-10 崩溃事故）**：界面型插件的 `client.js` 不是 ESM 模块——宿主把**所有插件的 client.js 拼成一个大脚本**加载。含 `export`/`import` 会让整个拼接脚本 `SyntaxError: Unexpected token 'export'`，**web boot 失败、整个 DSH 起不来**。

**完整插件集条款（2026-11-10 第二次崩溃）**：一次性 profile 如果只装待验插件（最小组合），**验不出插件间的冲突**。实测：同一插件在 3-bundle 的最小 profile 里能激活，混进完整 13+1 插件集就 `1 entry did not activate`，且宿主日志**没有 renderer 堆栈**（只有 `failed`），无法定位。

P3.5 要验「装进真实环境不炸」，一次性 profile 必须**复刻目标环境的完整插件集**（同 bundle 组合），而不是只装待验插件。最小 profile 只能验「代码能不能加载」，不能验「混进去会不会冲突」。



正确形态（picker / dshmarket / draft-studio 一致）：

```js
window.__ModuleLoader__.load({
  id: '<包名>',
  factory: (require) => {
    const plugin = { inject, apply /* , 纯逻辑 */ };
    Object.defineProperty(plugin, Symbol.toStringTag, { value: 'Module' });
    return plugin;
  },
});
```

P2 出口判据必须加两条：

- **断言 client.js 无 ESM 语法、有 `window.__ModuleLoader__.load` 注册**；
- **模拟宿主拼接大脚本 `new Function(combined)` parse 成功**——单文件 `node --check` 是合法 ESM，测不出这个错。

离线测试全绿 ≠ 宿主能加载：`node import()` 会把 ESM 当合法模块加载，DOM 桩直接 import 具名导出也全绿，**没有一条在验证宿主会怎么加载这个文件**。

**Host 半形态条款（2026-11-10 第二个崩溃点）**：`index.js` 的 `Config` **不是普通对象**。cordis 要求它是 schemastery Schema（有 `.validate()`）。写 `export const Config = {}` 会让插件 activate 直接失败：

```
warning: 1 entry did not activate
TypeError: Cannot read properties of undefined (reading 'validate')  at resolveConfig
```

**不需要用户可调配置时，正确做法是根本不导出 `Config`**（对照 `@wufeng0105/dsh-enhance`）。需要配置时才用 `Schema.object({...})`。

P2 出口判据再加两条断言：

- `Config` 若存在，`typeof Config.validate === 'function'` 且 `Config({})` 不抛；
- `index.js` 必须导出 `name` / `inject` / `apply` 三件套。

**为什么离线测不出**：`node --check` 与 `node import()` 都只看语法和模块合法性；这两条错都发生在**宿主加载与激活阶段**，只有真机启动会暴露。

**出口**：

- 每条需要 L1 的验收，要么通过并标 L1，要么写明"无法在运行时验证 + 原因 + 谁接受"；
- 一次性 profile 已删除；
- **日常 profile 未被改动**（跑前跑后对 `$DSH_PROFILE_DIR` 做哈希比对）。

**为什么单独一个阶段**：离线验证只能证明"代码路径通"，不能证明"装上能用"。三轮实验里运行时结论全部缺失，代价是"测试全绿但按钮点了没反应"这类问题只能靠猜。

### P4 交付

**入口**：P3 或 P3b 放行。

**产物**：可安装包 + 安装说明 + 验收走查表 + 已知问题清单。

**出口**：

- `files` 白名单与包内文件三方向差集为空，每个排除项写理由；
- `npm pack` 后从 tarball 真加载一次；
- 交付说明里的命令真跑过；
- 每个已知缺陷标注是否**阻断安装路径**；
- 说明书写明"装上后的预期现象"，让用户能区分 未装 / 已装未生效 / 坏了。

### P5 发布维护

**入口**：P4 交付物。

**产物**：触点清单 + 复检脚本 + 升级体检手册。

**出口**：

- 清单从**代码实际引用**倒推，不从计划抄；
- 每条带：引用点 / 代码位置 / 为什么非它不可 / 怎么探 / 不成立时怎么降级 / 验证状态；
- 复检脚本能变红（删一条触点必须报 MISSING）；
- 四态可判读（OK / MISSING / CHANGED / UNVERIFIABLE），无法自动判的单独列册。


---

判据之外的事——这套东西凭什么成立、它在哪里不成立、会付出什么代价——见 `evidence.md`。

## 怎么用

### 三个层次，按成本递增

| 层次 | 做什么 | 成本 | 适合 |
|---|---|---|---|
| **一** | 把 23 条铁律里最常踩的五条贴进项目 `AGENTS.md` | 五分钟 | 小改动、修 bug |
| **二** | 每个阶段结束时开一个审查员，按阶段卡判 | 每阶段一次调用 | **日常开发** |
| **三** | 全流程 P0–P5 + 触点清单 + 复检脚本 | 完整跑一遍 | 新插件、要发布 |

五条最常踩的：每条验收能判真假、每条宿主断言带出处、每阶段开独立审查员、任何检查先证明会红、模块存在不等于产品在用。

**建议从第二层开始。** 第一层太轻，挡不住"没接线"；第三层太重，容易半途放弃。

### 开审查员的一句话

阶段做完，对 AI 说：

> 开一个审查员，按 `process.md` 的阶段卡审这一版。需求在 `<需求文件>`，产物在 `<产物目录>`。它只读不写，只出三态结论。

审查员的任务书模板见 `reviewer.md`。

### 会付出什么代价

这套东西不是免费的。**收益侧有 23 条铁律，成本侧只有这四笔，必须一起看**：

| 成本 | 具体是什么 | 怎么估 |
|---|---|---|
| **每道门要人工触发** | 它不是 CI，不会自动跑。漏了开门，机制就等于不存在 | 一次真实开发里数「开了几次门」 |
| **每次改动要一次真机验证** | 建一次性 profile → 装 → 验 → 拆，约 2 分钟；**改动次数没有上界** | 数「改了几次、验了几次」 |
| **判据要靠事故喂养** | 23 条铁律没有一条是凭空想的，全是踩过之后补的 | 每遇到新事故，加一条；这是持续成本 |
| **工作方式要改造** | 项目里得有 `stages/` 目录、每阶段一个 `GATE.json`、根目录一个 marker | 迁移一次 + 每次产物的放置摩擦 |

**这四笔加起来的工时，可能超过收益。** 所以在真实项目上跑第一轮时，同时记三列：开门次数、每次开门的人工耗时、维护目录结构的耗时。

**事前写死一个止损线**（例如「额外耗时超过需求工期的 30% 就不划算」）。低于止损线 → 机制成立；高于 → 这是方向层面的反证，和「判据有没有用」同等重要。
