# plugin-kit

> DSH（DeepSeek Harness）插件开发流程 —— 一套从三轮真实开发事故里归纳出的**阶段门 + 审查员**机制。

**本目录是判据本体**：每个阶段该产出什么、谁来判断、什么算过。

它现在有两种分发形态：

| 形态 | 怎么用 | 有什么 |
|---|---|---|
| **独立 skill**（本目录） | 复制到 `<项目>/.dsh/skills/` 或 `~/.dsh/skills/` | 只有判据，靠**人工开门** |
| **插件**（`dsh-plugin-kit`） | `plugin_manager install_bundle` | 判据 + 常驻纪律段 + **机械拦截** |

两种用同一套判据，区别只在门怎么开。

## 它解决什么

三轮真实开发里，问题不是「写得不好」，而是**坏在看不见的地方**：

| 失败模式 | 具体形态 | 自评能发现吗 |
|---|---|---|
| **没接线** | 模块写了、测试全绿，产品代码没 import 它 | 不能 |
| **空真** | 「全关时与宿主一致」——当时压根没接线 | 不能 |
| **假绿** | 负例的观测字段不存在，永远不红 | 不能 |

共同点：**它们不在任何一段代码里，而在段与段之间**。逐段检查一律看不见。

## 怎么用

装进 DSH 的 skill 目录（项目级或用户级）：

```
<项目>/.dsh/skills/plugin-kit/    ← rank 100
~/.dsh/skills/plugin-kit/         ← rank 400
```

然后按 `SKILL.md` 的最短路径走。

### 最小起手（五条）

1. 每条验收必须能判真假；靠人看的要给机判替代。
2. 每条关于宿主的断言必须带出处（探测命令+返回，或安装包 `文件:行`）。
3. 每阶段结束开一个**新开的、只读的**审查员。
4. 任何检查先证明它会红，再用它判通过。
5. 模块存在 ≠ 产品在用：必须证明它在 import 图里可达。

## 与 DSH 内置 skill 的关系

DSH 自带 4 个 skill（`cordis-plugin-development` 等），讲**怎么用宿主的 API**。

这个 skill 讲**怎么确认自己用对了**。

判别轴不是「事实 vs 判断」，而是：

> **内置给你领域契约知识 + 零散的证据标准；这个 skill 给你一套可执行的裁决程序。**

碎片 vs 程序。程序需要角色、循环、结论格式——这些塞进知识文档会毁掉知识文档。

**技术细节不在本仓重复**：`references/tools.md` 里凡是会随宿主升级失效的命令参数，只写「去哪个内置 skill 找哪个主题」，不复制。

## 边界

三条最重要的（完整九条见 `references/evidence.md`）：

1. **"换人"从没真的换过**——三个阶段换了上下文，但同一模型、同一作者、同一机器、同一宿主版本。
2. **中间态不可复跑**——支撑铁律的事故证据是报告文字，不是可重放快照。
3. **审查员会误判**——它漏过也错过，只是比自评更可靠。

## 一句话

**把检查从写的人手里拿走，交给一个不参与写的审查员，能抓住自评永远抓不到的错。**

代价：判据是事故喂出来的；审查员会误判；中间态留不住。**门不必再人工开了**——插件形态用 `tools/pre-execute` 机械拦截。
